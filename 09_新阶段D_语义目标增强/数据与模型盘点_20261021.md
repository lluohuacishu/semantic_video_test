### D0 必须处理的实际问题

1. **帧名映射：** 例如 video001 的标注 `file_name=000000.png`，Frames 实际文件为 `video_001/frame_000000.jpg`。需要按视频身份、帧编号和时间建立显式映射，不能只按目录排序配对。
2. **7 段存在编号映射缺口：** video_027、037、041、042、044、045、054，简单按文件数字对齐时合计 165 个标注 frame_id 找不到同号图像。部分段总图像数相等，可能是编号或剪裁偏移；这次尚未视觉对齐，不能直接判断为数据损坏，更不能静默删掉或把后续帧依次顶上。
3. **类别名称：** video001 的 category 1 名为 `fish`，其余 53 份名为 `object`。作者说明数据目标为鱼，但导入器仍须抽查对象并固定映射，不能仅靠类别字符串丢掉大部分标注。
4. **标注格式：** 作者 README 提到 polygon，本地抽查为压缩 RLE。以实际 JSON 为准，核对尺寸、bbox/area 与解码掩码；掩码图的调色板/实例编码也须另核对。
5. **来源分组：** 54 份本地 metadata 内容完全相同：日期 22/05/2021、10 m、GoPro Hero 3、Palma's bay。不能据此宣称 54 个独立拍摄场景，也不能仅凭这组字段完成跨场景划分。需结合源视频、近重复检查与可得作者说明建立来源组；来源未知时明确标为“按序列留出、拍摄独立性未证实”。
6. **本地 README.txt 为空，未见固定 train/val/test 文件。** 不凭外部目录示例假设本包已有划分；版本、完整性及发布使用条件在正式数据登记时补齐。
7. **历史使用线索：** 后续代码盘点发现旧工程已有 `sfishtrack_001/027/054` 的真实编码及评价日志。须核实是否与新 ZIP 同源，核验前不列为全新盲测；仅凭这些日志不能推断曾用于模型训练。见 [路线评审与证据](D路线调整评审_20261021.md)。

建议 D0 先从确认对齐的少量序列建立索引，不必一次性展开整包。不能将同一视频的相邻帧随机分入训练和测试。GT 仅用于离线监督与评价；自动发送端的正式输入只能来自源 RGB 和预测结果。
