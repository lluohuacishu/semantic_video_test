日期：2026-10-27。目标是缩短文件任务总等待，最终在 Orin NX Super 16GB 上编码或解码。模型、量化参数与画质先保持不变，先消除整文件串行等待。旧轮次已收束，当前是独立优化阶段。

## 判断与已有证据

GLC 的 `NeuralCodec.frame()` 接受当前帧的 z/y 码流和已经解码的参考状态。I 帧重建建立参考，P 帧只使用过去的参考，没有等待未来帧的需求。网络结构无需重训练即可改成流水线；同一 GOP 仍要按依赖顺序执行，不能把全部 P 帧任意并行。

16 帧独立进程的真实 TCP 原型已经通过，详情见同目录《流水线原型结果_20261027.md》。首帧在整段编码和接收完成之前解码，码流和 RGB/参考状态逐帧校验通过。网页尚未接入，Orin 和真实水下链路尚未测试。

当前普通 GLC 的文件流程只是调度限制。语义路径的预处理也有整段准备步骤，所以先完成普通 GLC 原型；接入语义保护时，还要把预处理本身改成按帧或有界窗口输出，不能仅换传输函数就声称整条语义路径已经流式化。

## 建议的数据流

```mermaid
flowchart LR
    A[读取并准备一帧] --> B[发送端 GPU 编码]
    B --> C[有界发送队列]
    C --> D[封装 / 可选纠错与交织]
    D --> E[链路]
    E --> F[纠错与完整性校验]
    F --> G[有界接收队列]
    G --> H[接收端 GPU 顺序解码]
    H --> I[逐帧输出 / 最终归档]
```

网络任务与模型任务分别执行。编码出一帧即可入队；接收完整且通过校验的一帧即可解码。队列满时等待，形成反压，不无限累计 RGB 或压缩包；TCP 缓冲及正在处理的记录也需要计入内存预算。不能为了绕过坏包将错误参考状态传给后续 P 帧。

开始消息先提供模型、权重、运算配置、宽高、帧率、q、GOP 等信息。帧记录至少具有可验证的边界、帧序号和载荷完整性信息。结束消息给出实际帧数、总字节和最终摘要；只有正常结束并通过最终校验才把整个任务标为成功。提前解码的帧可以作为暂定结果，但截断文件不能被标成完整文件。

原型先支持明确的请求帧数，短输入直接失败。正式设计还要处理未知最终帧数：开始消息允许预计数量，结束消息确定实际数量，并在归档时产生正确的文件头。现有 GLCV v2 要求头部精确帧数，不能仅把它直接发出后忽略 EOF 差异。

## 原型选择及其限制

原型保留现有神经网络和 rANS，不修改 C5 生产路径。两个独立 Python 进程，各有网络线程与最多 2 条记录的队列；网络走本机 TCP，发送端按 40 kbps 限制应用层字节。发送端只读取原视频，接收端只读取网络消息和模型。

逐帧记录使用长度受限的固定头、头部 CRC、正文 SHA-256，并临时携带两组各 32 B 的逐帧 RGB/参考状态哈希，便于逐帧定位数值问题。结束时双方重建相同 GLCV v2 归档文件并核对 SHA-256。这里的校验是错误检测，不是 FEC，也不是身份认证。

诊断格式开销较大，不能直接作为低码率部署格式。下一步优先保留必要的序号、边界和载荷校验，研究把诊断用逐帧重建哈希移到分段/最终核验或离线日志。任何精简都要重新验证损坏、截断、乱序和数值不一致能够被正确处理，并分别统计真实发送字节和纯压缩载荷。

## 逐步实施顺序

1. **已完成：小规模机制验证。** 普通 GLC、FP32、原生 rANS，16 帧，证明首帧先于整段编码结束；检查与旧基线前缀一致。
2. **下一步：精简传输格式与有界任务接口。** 固定质量参数，支持明确的取消、超时、缺失结束消息、接收端失败通知和未知帧数收尾。当前原型是命令行机制证明，未覆盖这些生产生命周期测试。
3. **做同条件串行/流水线配对。** 相同帧数、质量、预览、暖机与设备条件，测试不同应用层速率；计入新增协议开销。记录编码完成、首帧可用、最后一帧可用、最终校验完成、队列等待和内存峰值。至少分别报告冷启动与模型常驻。
4. **接入已有网页和收发服务。** 提供编码/发送/接收/解码四组独立进度，支持取消和出错回收；保留整文件模式作为对照。提前解码不等于浏览器已支持播放，若要边看，预览输出还需独立的流式媒体机制。
5. **加入信道保护试验。** 明确通信设备接口与其已有纠错，测试随机/突发残余错误及丢包，比较纠错强度、交织缓冲、真实字节和完整成功率。不要把 TCP 自动重传掩盖后的效果当成 FEC 效果。
6. **Orin 部署和算子优化。** 在盒子上实测端点性能与功耗，再研究网络融合、数值安全的低精度、批处理/独立 GOP 并行；不从本机单 GPU 回环推算目标设备速度。

跨设备数值兼容必须单独验证：当前原型严格比较完整运算配置，RTX 与 Orin 的设备/环境字段不同会被拒绝。后续要验证两端概率表索引、参考状态和重建的一致性，再建立支持的兼容策略；不能删除这项检查后就宣称跨设备可用。

## 误码处理接口

纠错与交织放在网络载荷交付给 GLC 之前。按帧或有限块组织可减少等待；跨多帧交织需要等对应窗口，深度应作为延迟与抗突发错误的权衡参数。头部、帧序号、长度和 I 帧同样需要保护，不能只保护图像数据字节。

对来自调制解调器的原始带错字节，研究错误纠正码；对已由设备校验并丢弃坏包的接口，研究包级纠删恢复。两者不可混为同一个“误码率”。超出纠错能力时不能继续污染参考链：可补传，或按显式恢复策略跳到独立 I 帧并标记缺失区段；后者不算完整文件恢复。当前二者均未接入原型。

## 如何判断有没有收益

串行任务约为编码 + 传输 + 解码。流水线应直接测实际完成时间；不同帧大小、I/P 耗时、队列与纠错窗口都会影响结果，不能把历史三个总时间简单取最大值当作实测。两台设备可以重叠 GPU 计算；同一台电脑上两个进程争用一块 GPU，结果仅作为机制与资源检查。

原 D 预算和语义结果按原协议保存。本阶段必须披露协议和纠错冗余，原型成功不能被当作满足原 40 kbps / 10% 文件预算或水下应用验收。
