核对日期：2026-10-17。本页是文献和代码事实；本轮试验与选型结论另见本目录的结果报告。旧 A–F 的编号不延续到这里。

## GLC-Video 实际提供什么

GLC 在生成模型的潜空间压缩，利用时空先验减少冗余，并通过训练损失改善语义一致性。论文的重点是低码率下的感知质量，不能把它直接等同于鱼类、潜水员的任务保真。文中视频部分的 65.3% 节省，以 PLVC 为对照、以 DISTS 为评价，不能写成相对 H.265 的普遍收益。图像前作是 CVPR 2024，图像与视频扩展是 2025 年论文；其视频实验采用 96 帧、单初始 I 帧等条件，与我们的 GOP32 不同。论文也讨论了时序稳定性局限。来源：[图像与视频论文](https://arxiv.org/html/2505.16177v1)。

作者仓库提供预训练测试、图像与视频权重，许可证为 Apache-2.0；当前检出的代码中没有完整的 GLC 专用训练入口。仓库里的 LPIPS `trainer.py` 不是 GLC 视频训练管线。来源：[作者仓库](https://github.com/jzyustc/GLC)。

本机已固定到 `126db25f9c093508cd0c99cee32b53fd60074f9a`，与本次查到的远端主分支一致，工作树干净。对这份源码逐项检查：

| 检查点 | 事实与含义 |
|---|---|
| `test_video.py` | 调用 I/P 模型的 `test()`，记录重建图和 JSON；`.bin` 路径变量本身不代表生成了可独立解码的码流 |
| `src/models/video_model.py` | y 的比特数来自概率模型估计，z 的索引长度另计；不能将测试 JSON 的估计字节直接用于链路发送 |
| 本地 `glc_video_codec.py` | 复用作者网络和权重，增加离散索引、真实 rANS、容器、检查和独立解码。这是既有自定义接口，不是官方标准格式 |
| 模型预共享 | I 权重 667,371,692 B，P 权重 502,245,134 B，合计 1,169,616,826 B。每段文件可不重复携带；接收端须先具备模型与环境 |
| 算术一致性 | 本地码流要求匹配推理配置，并逐帧检查潜变量与 RGB 哈希；不同 GPU、不同框架版本及 CPU 接收端的兼容性尚未证明 |
| 语义条件 | 当前适配器没有鱼类掩码或潜水员 ROI 输入。直接换成 GLC，不能声称完成了目标优先的语义编码 |

相关本地实现：[GLC 适配说明](<../04_外部依赖快照/semantic-video-training/docs/GLC-Video.md>)、[真实码流适配器](<../04_外部依赖快照/semantic-video-training/scripts/glc_video_codec.py>)。上游对应代码：[固定版本的测试入口](https://github.com/jzyustc/GLC/blob/126db25f9c093508cd0c99cee32b53fd60074f9a/test_video.py)、[固定版本的视频模型](https://github.com/jzyustc/GLC/blob/126db25f9c093508cd0c99cee32b53fd60074f9a/src/models/video_model.py)。

## 其他候选，以及与现有工程的关系

| 候选 | 可复用内容 | 本阶段应如何使用 |
|---|---|---|
| H.265 / x265 | 现有 FFmpeg、收发链路和解码；上游已经有 ROI 到量化偏移的接口 | 强基线与语义画质分配候选。离线时允许 B 帧、前视，不继续沿用不必要的低延迟约束 |
| AV1 / libaom | 本机 FFmpeg 已提供编码器，不需要安装新环境 | 本轮直接测完整文件和重建质量；不把未验证的动态 ROI 支持当作现成能力 |
| MLVC-S | 本地已有真实码流、模型和评价代码；作者提供训练与实际熵编码组件 | 保留神经编码对照。官方还提供感知预训练模型，若以后需要，应先测它，再考虑自行训练 |
| DCVC-UF | 当前作者仓库已有训练代码、真实熵编码与融合推理组件 | 新候选；本轮未迁移环境、未实测。当前说明涉及 CUDA 13、C++/CUDA 扩展和 CUTLASS，不能把服务器速度直接代入本机 |
| VVC / VVenC | 已有开源编码器，可作为更强离线锚点 | 本机当前 FFmpeg 没有 libvvenc，本轮未跑；不声称已比较过或不如其他候选 |
| AccMPEG 思路 | 用任务信息决定空间画质分配 | 参考其任务感知编码方法；其旧 H.264 修改版与依赖不适合直接替换整个工程 |

来源：[FFmpeg 编码器说明](https://ffmpeg.org/ffmpeg-codecs.html)、[x265 预设](https://x265.readthedocs.io/en/stable/presets.html)、[MLVC 官方仓库](https://github.com/microsoft/mlvc)、[DCVC 官方仓库](https://github.com/microsoft/DCVC)、[VVenC 官方仓库](https://github.com/fraunhoferhhi/vvenc)、[AccMPEG 论文](https://arxiv.org/abs/2204.12534)与[代码](https://github.com/KuntaiDu/AccMPEG)。

## 哪些属于必要适配，哪些可以少做

现有工作没有重新发明 GLC 神经网络；真正新增的是文件协议、熵编码适配与收发验证。由于作者测试入口没有现成真实码流，这部分当时有实际作用。若后续主线转向标准编码器，它就成为需要保留但不必继续扩展的研究分支。

旧“半分辨率背景 + 原分辨率 ROI 双流 + 接收端贴回”的方法能够工作，但自己维护了裁切布局、额外编码流、打包和融合边界。下一步应先验证标准编码器原有的 ROI 量化接口，争取让接收端只解码一个标准视频文件。保留旧双流作为对照和回退，不能在尚未验证时删除。

这一判断有源码依据：FFmpeg 的 [libx265 适配层](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/libavcodec/libx265.c)把每帧 ROI side data 转成 `quantOffsets`，且要求启用 AQ。它证明底层能力存在，**不证明我们的动态鱼区已接入**。[addroi 滤镜](https://ffmpeg.org/ffmpeg-filters.html#addroi)可以验证固定区域，移动目标仍需要逐帧注入正确区域、检查帧序与实际码流效果。

本轮没有训练、下载新大模型或开发上述动态 ROI。选型应围绕“目标可辨识、整幅视频可观看、真实完整文件较小、接收端能可靠恢复”，不围绕模型名称是否带有 semantic / generative。
