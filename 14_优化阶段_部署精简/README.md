# GLC 按发送 / 接收角色精简部署

2026-10-29。沿用 `codex/glc-sender-no-rgb` 分支；前一阶段已证明发送端跳过RGB生成而保持码流载荷及接收画面一致。本阶段检查实际收发中用不到的模块、权重及诊断输出，不训练、不替换学生、不改变FP32精度。

**[实测与复现结果](部署精简实测_20261029.md)已完成**：发送/接收角色各三个设置、三组配对，共36次主测量及2次仅剥离观察；保留原码流和RGB。640×360发送峰值显存1639→1071 MiB，接收1520→1006 MiB。额外核心加速很小，主要收益是内存、存储、模型加载及精简实际文件输出。46项CPU检查和真实视频闭环/失败不发布验证通过。

## 哪些可以去掉

| 内容 | 水下发送端 | 岸上接收端 | 原因 |
|---|---|---|---|
| `image.code_pred_loss`、`code_pred_pix_loss` | 去掉 | 去掉 | 训练用预测损失网络，合计55,154,688参数，当前实际码流路径不调用 |
| I/P的`vqgan.quantize` | 去掉 | 去掉 | 当前使用另外的`z_vq`，这两套另注册的量化器共8,388,608参数没有调用；不假定两套权重相同 |
| I/P的`vqgan.generator` | 去掉 | 保留完整原权重 | 发送端不用显示RGB；接收端必须恢复可观看视频 |
| I/P的`vqgan.encoder` | 保留 | 去掉 | 输入图像编码只在发送端执行 |
| I的`enc/hyper_enc/q_enc` | 保留 | 去掉 | 只用于产生编码符号，接收端不需要 |
| P的`encoder/temporal_cond/y_temporal_combine/hyper_tokenizer/y_q_enc` | 保留 | 去掉 | 只在有原始输入的编码分支调用 |
| I的`dec`、P的`decoder`和`z_vq` | 保留 | 保留 | 发送端也必须重建潜变量以维护参考链，不能因名字有decoder就删除 |
| P的上下文、权重图、逆tokenizer、先验及参考适配器 | 保留 | 保留 | 两端都依赖它们解释码流、更新参考，包含GOP/重置后的不同分支 |

剥离在`meta`模型上完成，之后才加载保留张量，避免先分配整个模型再删除。角色权重中的每个保留张量来自已核验SHA-256的官方检查点，键、形状、dtype及有限值严格检查；缺失模块调用即报错，不返回假张量。接收端CPU插值的q_dec与旧适配器采用相同运算顺序。

官方两份检查点合计1,169,616,826 B。导出的发送角色两文件合计563,177,284 B，接收角色合计618,622,240 B，分别减少51.85%和47.11%。部署到某台设备时只需对应角色的两文件及manifest，不必复制另一个角色的权重。仓库不上传这些大文件，官方原权重保持不变。

## 编码 / 解码中减少的重复计算

`RoleCodec(optimize=True)`尝试三个保持原始数值的改写：

1. 将z码本还原的一热大矩阵乘法改为直接查embedding表，两端都适用。
2. 发送端码本距离中的`(embedding.weight ** 2).sum(1)`只算一次，保留FP32表达式的运算顺序。
3. 缓存不变的布尔掩码，并将编码每阶段的scale和整数符号合并为一次GPU到CPU传输。CDF索引仍在CPU按原float64规则计算，未更改量化/概率表规则。

这些改写是否带来稳定速度收益须看配对实测；删除本来没有执行的网络主要减少存储、显存和加载开销，不能直接算作每帧算力节省。接收端主要的RGB生成仍然保留，不能把它当作“无用功能”删除。

## 实际运行不需要的输出

[最简文件入口](deploy_codec.py)只提供“视频→发送文件”和“发送文件→一份可观看视频”。发送端不生成原视频预览、重建预览或语义输入预览；两端不写PNG序列、PSNR对照、逐帧诊断JSON及原图像素摘要。接收端输出视频仍保留。全文件SHA-256和有序参考状态校验继续执行，未用取消校验换速度。

旧C1的`display`模式已经不写PNG，因此不能把“不写PNG”重复算成新增性能收益；旧入口的显示预览、指标、调试功能也没有被删除或默认切换。新增的`MemoryFrames(..., collect_hashes=False)`只供最简发送入口使用，默认行为不变。

```powershell
$glcPython = 'C:\Users\lenovo\Desktop\works\work\semantic-video-training\.venv-glc\Scripts\python.exe'
$deploy = '14_优化阶段_部署精简/deploy_codec.py'
# 各输出必须使用新的目录，避免覆盖既有结果。
& $glcPython -X utf8 $deploy export --output 'C:\新的角色权重目录'
& $glcPython -X utf8 $deploy encode --assets 'C:\新的角色权重目录' --input 'C:\输入视频.mkv' --output 'C:\新的发送任务目录' --width 640 --stride 2 --q 0
& $glcPython -X utf8 $deploy decode --assets 'C:\新的角色权重目录' --input 'C:\新的发送任务目录\stream.glcsnd' --output 'C:\新的接收任务目录'
```

默认最多处理10,000帧，保留原GLCSND01的256MiB文件上限，实际EOF确定帧数。接收器先验证整文件，再独立解码核验参考状态；视频以临时文件接收RGB，只有全部参考状态通过才发布`video.mp4`。该MP4是H.264观看输出，不是水下发送载荷。新入口只接受同运算配置，跨设备需另行明确验证。

## 验证入口与限制

[按角色测试](test_role_codec.py)检查被删模块、保留参考链、错误角色、权重状态检查及CPU数值；[配对控制器](run_benchmark.py)复用上轮三个输入，对发送/接收角色各做三组原模型与精简模式交替配对，并在首片增加仅剥离权重的单次观察。基线发送端已经免RGB，因此不能把本轮额外收益与上轮2.2倍混为一次配对测量。

本轮不测Orin、功耗、FEC或真实水声链路，也不切换生产网页。模型常驻可避免每个文件重复加载；长任务继续需要有界缓冲、参考状态隔离及完整性验证。精度转换、TensorRT、输入编码器蒸馏或生成器替换均不属于本次“删除无用功能”，需要单独验收。
