# C2 阶段进展：热点复测与原生 rANS 候选

日期：2026-10-19。**C2 未完成验收，已按用户断电通知暂停，明日继续。** 收尾时没有运行中的实验。最新状态见 [接续记录](C2接续记录_20261019.md)，操作见 [复现说明](C2复现说明.md)，小型机器证据见 [检查点](c2_checkpoint_20261019.json)。

## 1. 回应外部评价

- C1 的约 30% 科研 / 37% 展示收益只由 compact 的三组成对实验支持，其他三档不能据兼容性单次记录推算相同收益。
- C0 的熵耗时不再直接套入 C1。先对 C1 展示路径复测，再选择 C2 候选。
- C1 两次中断的原因仍未知。新增记录用于捕获之后的异常、退出与失联证据，不能追认历史原因。

## 2. C1 展示路径热点复测

`C2_diagnose66_20261019_r1`：compact，连续 66 帧，原 FP32 确定性神经流程和 Python 熵编码。编码、接收端在独立进程串行执行，各自先做 8 帧冷态预热，再做一个埋点开/关常驻对照；解码端顺序反转。六个任务全部通过冻结 B4 校验，66 帧覆盖 I 帧和 reset32 状态边界。

| 方向 | 无埋点，到预览就绪 | 有埋点，到预览就绪 | 有埋点的熵索引+rANS | 占有埋点任务 |
|---|---:|---:|---:|---:|
| 编码 | 19.769 s | 19.794 s | 3.593 s | 18.15% |
| 独立解码 | 13.966 s | 14.003 s | 3.779 s | 26.98% |
| 两端分别执行之和 | 33.736 s | 33.797 s | 7.372 s | 21.81% |

开关总差约 0.18%，只有单对，含顺序和机器波动，不能作为精确埋点开销估计。所有时间都是 CPU 墙钟作用域：`frame` 包含网络、等待、搬运与嵌套熵调用；熵作用域不包含此前 `.cpu().numpy()` 的等待/搬运。不能把嵌套作用域相加，也不能把它们称为 GPU 忙碌时间。

这不是完整 125 帧的热点比例，也不是其他三档的比例。若把该诊断中整个熵作用域理想化为零，整体最多减少约 21.8%、约 1.28×；实际原生适配仍保留索引、校验、内存和调用开销，因此必须另测组合后的整段时间。

## 3. 选择与实现

选择候选 A，暂不启动 GPU 编译候选。`native/glc_rans.c` 复用固定版本 Fabian Giesen public-domain byte-rANS 基础算子，并适配已有本地大端长度头、低端状态字、escape 和严格尾状态校验。接收端自行检查边界后归一化；不使用不检查末尾的读取函数。

`c2_native.py` 是显式启用的 ctypes 包装；原 `glc_entropy.py` 不变，保留作参考与回退。CDF、浮点 scale 索引、模型/权重、FP32 算术、四档参数、容器 v2、通信包标识及 RGB/潜变量校验均不变。

现有 GCC 可构建，不安装或升级环境。前两次构建失败保留；定位到默认目标目录的汇编器返回 `0xC0000135`，通过指定同套工具中可工作的 bin 子程序完成构建。源码、固定上游头、编译命令、返回码和 DLL 哈希均落盘。

## 4. 已过门槛

- 10 项原生 CPU 测试覆盖 128 张表、int32 极值、空/非连续输入、截断、坏头和非规范 escape；另有 1,500 次定种子码流变异，旧新接受/拒绝和输出一致。
- 5 项监督器测试覆盖真实正常/异常退出、启动失败、PID 重用/孤儿识别和最后进度保存。
- `C2_gate8_20261019_r1`、`C2_gate66_20261019_r1` 各 6 个视频任务通过；两个编码完整流逐字节一致，Python/native 四个交叉解码方向通过 B4 的载荷、重建 RGB、潜变量及预览校验。
- 门槛任务混合首次/常驻状态，不能直接相减来声称整体提速。完整性能证据单独运行。

## 5. 性能与剩余项

`C2_compact_pairs_20261019_r1` 已完成：compact 完整 125 帧，Python/native 各端三对，AB/BA 交错、正式任务无热点埋点。12 个正式任务与 4 个单列预热均通过，6 个完整编码流逐字节匹配 B4。两端合计按相同 pair 的编码+解码相加后取中位数，不把各端中位数简单相加。

| 到 MP4 就绪 | C1 Python 熵实现 | C1+原生熵实现 | 配对时间降幅中位数 |
|---|---:|---:|---:|
| 编码 | 37.581 s | 30.650 s | 18.58% |
| 独立解码 | 26.472 s | 19.338 s | 26.75% |
| 两端分别执行之和 | 64.068 s | 49.943 s | 22.05% |

两端配对节省中位数 14.130 s，三个合计候选值范围 49.938–50.156 s；三对降幅 21.63%–22.28%，不能用三次样本估计可靠 p95。同期 C1 参考略快于此前 C1 报告的 65.010 s，新增收益使用本次参考 64.068 s 计算，不用较慢历史值扩大 C2 增益。

若仅按用户指定的 C1 既有展示参考 103.454 s 折算，49.943 s 约为其 2.07× 加速，低于 51.727 s 的数值挑战线。但本轮没有重跑 legacy/C2 同期配对，因此不能把该跨批次折算写成最终组合 2× 已验收；主要正式结论是 C2 相对同期 C1 的 22.05% 增益。

最新通过 53 项 C0/C1/C2 与 55 项 B 回归，共 **108 项**，日志和退出码在 `C2_checks_20261019_r5`，此前 r1–r4 保留。覆盖配对汇总、部分任务排除、孤儿进程恢复阻止、进程返回 0 但缺结果时拒绝通过、第二素材同片参考、真实 Windows 文件锁重试，以及实际 worker 与启动器 PID 区分。

## 6. 稳定性与恢复

监督器持久化子进程/监督器 PID 与创建时间、返回码、起止时间和心跳；工作进程在重依赖导入前启用 `faulthandler`，另记 2 秒心跳、最后完成帧、异常栈及预览状态。重启后的只读检查可识别陈旧 running 和仍在运行的孤儿，不根据旧 JSON 自动重跑。

`STOP_REQUESTED` 在帧/预览边界取消后续任务，未完成样本排除且保留。离线恢复工具仅校验已落盘完整终态，不启动推理、不补造退出码。此机制不能保证捕获断电或操作系统强制结束的最后事件，也尚不等于 C3 网页长期稳定性验收。

本轮捕获到一次明确的日志层失败：第二素材编码进程在 2026-10-19 23:13:02（UTC+8）以 1 / `0x00000001` 退出，异常栈为 `heartbeat.json.tmp` 替换 `heartbeat.json` 时的 `PermissionError: [WinError 5]`。具体占用进程未确定；这不是 C1 两次历史中断原因的证据。已为 WinError 5/32/33 增加最多 10 次有界退避重试，永久错误仍抛出，并通过真实 Windows reader-lock 测试。修复尚待次日新视频任务验证。

检查同时发现 Windows venv 启动器和实际 Python worker 的 PID 可不同，现两者均按创建时间核查。已记录退出码但实际 worker 存活查询不确定、或心跳读取失败时的保守处理，列为明日恢复前待补强项。
