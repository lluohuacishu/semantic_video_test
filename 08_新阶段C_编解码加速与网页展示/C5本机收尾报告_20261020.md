# C5 本机收尾与接收端候选版

日期：2026-10-20。状态：**本机范围完成，可准备迁移；真实 4060 Laptop → 4070 Laptop 验收待接收机到位。** 当前不是整个 C5 的双机最终验收结论。

本会话接续“规划C5收尾与收发端分离”，没有排查原会话报错。保留 C5-0 至 C5-3 的提交和证据；核实原会话结束前的稳定性任务已经完成，未重跑该批任务。机器汇总见 [c5_summary_20261020.json](c5_summary_20261020.json)，操作见 [C5双机操作说明](C5双机操作说明.md)。

## 已完成的功能

- 独立发送端和接收端，各有页面、配置、任务目录与状态。原视频只在发送端；接收端通过真实 TCP 接收完整 `.glcv`，独立校验、解码、播放和下载。
- 接收端选择最大速度、20 kbps、40 kbps；发送端按预约快照执行应用层节流。画质和传输速度独立，既有码流可重发。
- 遵照用户执行中调整，**本机只做最大速度实验**。20/40 kbps 有虚拟时钟与档位快照测试，没有真实限速成绩，也不自动安排双机限速矩阵。
- 按实际 PTS 支持前 10 秒、指定区间与完整视频；compact/detail 输出 12.5 fps，motion/detail_motion 输出 25 fps；旧 frame/stride 路径保持。
- 可选单角色常驻，首次显式任务才加载模型；支持空闲释放，取消/失败后丢弃 worker、后继任务重新初始化。本机默认 cold。
- 严格 arithmetic 判定保留；设备配对诊断仅放宽 GPU 名称这一项，每条流仍需完整 SHA、RGB 和 latent 校验。未将 4070 标为已经兼容。

## 本机验收结果

| 项目 | 实际结果 | 范围 |
|---|---|---|
| 时间轴集成 | 旧 8 帧、主片 10 秒、NOAA 10 秒和全片均通过 | 既有 C5-1 证据；全片 346 帧/27.68 秒 |
| 独立端点连续序列 | 10 个成功任务 | 3 个完整 10 秒 compact、6 个四档代表短片、1 个 60 秒任务；全部 loopback/max/cold |
| 60 秒任务 | 750 帧、83,810 B；脚本墙钟 101.722 秒 | NOAA 循环生成的 **320×180** 输入；不是 640 宽的完整 60 秒性能成绩 |
| 编码取消 | 约 1.297 秒达到 cancelled | 已观察到真实 GPU 帧进度后取消 |
| 接收取消 | 约 0.309 秒达到 cancelled | max 发送部分数据后停生产者；未发布不完整码流 |
| 解码取消 | 约 1.092 秒，两端均 cancelled | 从发送端请求取消已开始的远端解码 |
| 常驻生命周期 | 每角色 10 次 8 帧任务；全部通过 | 编码取消、解码损坏流拒绝后均换新 PID 并成功恢复；不同时驻留两个角色 |
| 独立迁移副本 | 8 帧和完整 125 帧的 TCP 接收、CUDA 解码、MP4/码流下载摘要通过 | 代码、GLC、权重、FFmpeg、DLL 使用副本；复用本机 Python 环境 |
| 浏览器 | 两端历史任务正常显示，接收端 10 秒 MP4 实际播放至结尾，无控制台错误 | 既有 NOAA 125 帧结果回放；不是新任务点击至可播放计时 |
| 回归 | C 目录 134 项全部通过、无跳过 | 本会话重跑，含 native、时间轴、端点、常驻、部署摘要校验 |
| B 回归 | 55 项通过、无跳过 | 沿用原会话本日同版本记录；本次未改 B 代码 |

`check_c5.py` 已重新读取连续任务的发送/接收文件和 decode.json，核对完整 SHA、容器、RGB/latent 聚合摘要、帧数、源视频读取为空、输出 MP4 存在，以及常驻复用/恢复和回归记录。不是只检查 summary.json 中的 passed 字段。

常驻的 10 次短任务中，每角色空闲 allocated 均保持约 1149.84 MiB；reserved 编码 1774 MiB、解码 1804 MiB。取消和故意损坏的 worker 终态分别为 cancelled/failed，恢复 worker 完成后正常退出。未记录完整主机 RSS 趋势，不能据此声称长期无内存泄漏。

## 性能结论与停止边界

沿用 C5-3 三对交错实验：冷态独立编码/解码派发之和约 67.978、67.788、68.211 秒；热态约 56.781、56.874、56.973 秒，逐对降幅中位数 **16.47%**。这是角色派发耗时之和，排除了网页、网络和排队；不是实际跨机端到端时延。**网页 52 秒目标、40 秒挑战均未验证。**

采用可选常驻并保留 cold 回退，不追加 CUDA Graph/torch.compile 环境迁移或挑样。C2 同期 1.991×、严格 2× 未达到、语义 ROI 等预算净收益未证实和未做真实水声验证等历史结论不变。

## 交付与迁移

正式本地接收端目录：`01_项目/交付/C5接收端_20261020/`。根目录有 `先读我.txt` 与 `bundle_manifest.json`，内部为 `semantic_video_test`。目录含固定 revision 的 GLC 源码、两份已知权重、FFmpeg/FFprobe、native DLL、网页和脚本；不含 Python venv、连接口令、发送原视频或历史任务。

- `package_c5_receiver.py` 从实际 GLC HEAD 克隆并固定 checkout，记录生成时主仓库提交与脏工作区标识，逐文件保存大小及 SHA-256。生成后自动复核；`--verify` 可重新检查。
- `setup_c5_receiver.ps1` / `安装C5接收环境.cmd` 要求 Python 3.12，先核验资产，再创建独立 venv，安装 PyTorch 2.5.1/torchvision 0.20.1 cu124 及发送机观测依赖锁，执行 `pip check` 与路径检查。
- `requirements-c5-receiver-lock.txt` 来自发送端实际 `pip freeze`，没有猜测版本。现有环境不被覆盖；安装失败保留新环境和日志供检查。
- 本机已验证独立目录中真实接收端工作的资产依赖闭包；**未在干净系统新装 Python 依赖，也未在 4070 上运行安装器**。安装脚本已做 PowerShell 语法检查，不能把它等同于目标机安装通过。
- 8 帧、主片 125 帧、NOAA 125 帧的测试码流放在发送机 `01_项目/交付/C5发送测试码流_20261020/`；125 帧已覆盖 reset32/GOP64，可作为“至少 66 帧”门槛，不额外编码一条 66 帧流。

接收机到位后先安装、自检、设备配对，再按最大速度依次发送 8 帧、125 帧主片和 NOAA。保留严格结果校验；一旦重建摘要不一致，保存任务和环境证据，不把文件送达当作兼容成功。之后补其余画质代表任务与真实局域网中断恢复，完成双机最终验收。
