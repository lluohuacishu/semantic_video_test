2026-10-21 用户指定本问题作为 C7。状态：**C7-0 故障基线与 C7-1 诊断工具完成；数值原因、兼容修复和双机验收尚未完成。** 保留此前阶段编号，不另行推定 C6 的内容。

## 已确认的问题

用户给出的 `received (4).glcv` 为 356,604 B，SHA-256 为
`36162a828fd8fce8f07d8496ac3f7aa59a66ba6735d6dd6b1b1470c0f1d8853f`。
下载文件、4070 失败任务中的收到文件，以及 4060 本机原始编码/收到文件完全一致；容器 v2 的文件摘要和 1239 个压缩帧结构均通过离线核验。

- 输出为 640×360、约 15 fps、1239 帧。既有 4060 编码和本机独立解码记录的全部逐帧 RGB/latent 摘要相同，并与码流中的有序汇总摘要相同。
- 4070 任务 `d98161cd3cd441968fc250dac8acfe6e` 跑完 1239 帧，任务计时 415.303 秒，最后报 `Ordered GLC frame checksum aggregate differs from the sender.`
- 接收设置为 `device_pair_test`；准入记录只报告 GPU 名称不同。软件报告的 torch/CUDA/cuDNN/计算能力/TF32/确定性设置一致。该模式仅允许试验，不表示重建已验证。
- 失败任务记录的 15 个 C 层源码摘要与已发布 `3401050` 版本一致。后来源视频帧率/尺寸适配没有改动解码核心、熵编码器或容器规则。
- 旧失败路径没有保存实际汇总值和逐帧摘要，因此不能确定 RGB、latent 哪项不同、首个差异帧或差异大小。未证明具体 CUDA 算子是根因。

同学先前的 4070 自编自解通过与本次跨 GPU 失败并不矛盾。当前结论是：**这份流的 4060 → 4070 一致性验收失败**，不外推所有素材都失败，也不声称文件已损坏。

## 后续报告带来的范围收缩

用户随后提供 `glcv跨设备解码实验_20261021.md`，并补齐 `force_decode_glcv.py` 和 `forced_decode.json`。已静态检查脚本及 JSON，没有执行外部脚本或重跑视频。发送端的两个值与本机实际码流一致，JSON 记录了完整 1239 帧及下列结果：

|---|---|---|
| latent | `806d6681ab29471f95714e8ae7f6f4fce3d48c25fd6a7605416d34384b22bcc2` | 相同 |
| RGB | `a4b67eb3910a2c9be8a0c52ba000e35147fac55989b0b66489cb7a5bd6b8b894` | `8abed29931057c87ee6e495c1d361828439dd13edd2bb6f55c387c54095a680f` |

据 `reference_hash()` 和 `NeuralCodec.frame()`，latent 汇总包含每帧 `ref_latent`、`ref_y` 的字节摘要。该结果强烈支持这次独立脚本运行的帧间参考状态在两机一致，优先排查 `vqgan.generator` 到 `rgb_array` 的输出路径。无需为再次证明这一点重跑长片。

脚本核对结果：自定义 `Seq` 的域分隔、帧序号编码及逐帧哈希累计方式与容器相同；确实调用 `NeuralCodec(..., decoder_only=True)`，未看到改写网络计算或替换 `frame()`。它修改了内存中的 GPU 名称，但 `frame()` 的计算不使用该字段，因此这一步本身不修复数值差异。需补充：**该独立脚本沿用 Python GaussianRans，原失败任务采用 native 后端**；两次不是完全相同的执行路径。脚本的四项前置比较只打印布尔值，没有强制中止；本次码流字段已独立核对正确，不能将脚本原样当通用验收器。JSON 没有完整输入 SHA、逐帧结果和运行时代码指纹，当前审核属于外部实机证据审阅，不冒充本机重现实验。

必须保留以下区别：

- 最终 RGB 生成器也是神经网络，包含卷积、残差块、注意力矩阵乘/softmax、归一化和上采样。仅凭报告不能把根因锁定为插值，也不能外推所有主体算子在所有素材上都逐位一致。
- 参考状态一致并不能量化最终画面误差。报告没有两机原始 RGB 像素对照，“完全可用/语义不受影响”属于观察或推断。两边分别经过有损压缩的预览 MP4 也不适合量化原始像素误差。
- v2 容器只保存每帧哈希的有序汇总，与网页 `compact` 画质预设是两个概念。
- 报告的 A 方案（latent 阻断、RGB 记录）可以作为后续明确命名的跨设备预览策略来评估；若采用，必须显示“参考状态一致、RGB 不逐位一致/画面误差未验收”，不能标为全部校验通过。当前 `strict`、`device_pair_test` 的既有标准本次不变。
- 报告的 B 方案需要独立的发送端 RGB 参考。不能从 SHA-256 反推出 PSNR/MAE，也不能为在线独立解码要求重新传一整份原视频。

因此 C7-2 调整为：已完成对方脚本/JSON 静态复核，复用已有整段结果；只在需要量化或定位时，手动运行两端相同短样本及相同熵后端，比较保存的首帧/首个差异帧。当前诊断包已支持这些输出。后续优先量化 RGB 差异、定位生成器，再决定修正数值实现或增加有明确边界的预览策略；不自动采纳外部文档中的校验放宽建议。

诊断工具记录每帧 RGB 与 latent 的预期/实际摘要、各熵分段的 CDF 索引和解码符号摘要，并保存首帧及首个差异帧的 RGB/参考张量。遇到第一处差异即退出失败；`sample_passed` 仅表示短样本通过。工具不生成被标记为正常结果的视频。

优先区分以下情况，再动数值实现：

1. CDF 索引/离散符号先不同：排查熵概率计算、表索引量化和参考状态反馈；保证两端离散编码决策一致。
2. 离散符号相同、浮点参考状态不同：测量具体张量偏差，定位 GPU 运算或执行路径，再选择可复现实现。不能只删除 latent 哈希后宣布兼容。
3. 参考状态相同、最终 RGB 不同：定位图像生成和像素转换路径。

若必须改变参与编解码的数值规则，需要给新算术实现明确版本，两端同时升级并重新编码；旧流是否兼容单独说明。不能让旧流在接收端悄悄换算法，也不自动降到 CPU 后假定可以解旧 GPU 流。

PyTorch 文档说明浮点计算不保证跨平台逐位一致；这是排查依据，不是对这次具体算子的定论：[Numerical accuracy](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html)。
