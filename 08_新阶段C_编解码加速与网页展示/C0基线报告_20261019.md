## 2. 执行与恢复记录

正式矩阵为 18 个任务，另有 2 个 66 帧诊断任务：

- `compact`：编码、解码各 3 次独立进程首次任务，及各 3 次同进程常驻后续任务。
- `detail`、`motion`、`detail_motion`：各完成 1 次编码和 1 次独立解码，用于四档兼容筛查。
- 诊断覆盖第 0/32/64 帧边界，在第 1、33、64 帧保留短 Profiler 窗口；诊断码流前缀与 B4 对应载荷一致。

两次不完整会话分别停在 `C0_20261019_r2/diagnostic_encode` 第 26/66 帧和 `C0_20261019_r3/compact_encode_resident/warm3` 第 68/125 帧；两者均无 timing、validation、进程返回码或 Python traceback。半成品已排除，现存 Windows 应用日志也没有对应崩溃事件，因而可以确认执行被中断，但无法从现存记录判定 UI 闪退的根因。随后以新进程完成 `compact_encode_recovery/cold2` 与 `warm3`，两项均返回码 0 并通过校验；所有计入汇总的任务均有完整 timing 和 validation。

## 3. 正式耗时结果

单位均为秒；三次样本报告中位数和最小–最大范围，单次档位不作稳定性推断。

| 档位 | 方向 | 首次任务 `evidence_ready` | 常驻后续任务 `evidence_ready` |
| --- | --- | ---: | ---: |
| `compact` | 编码 | 74.04（71.18–93.57）；进程启动至就绪 75.48（72.67–95.19） | 69.71（69.67–84.94） |
| `compact` | 解码 | 46.08（45.78–46.14）；进程启动至就绪 47.64（47.21–47.64） | 41.86（41.68–42.05） |
| `detail` | 编码 | 152.84 | — |
| `detail` | 解码 | 93.61 | — |
| `motion` | 编码 | 146.13 | — |
| `motion` | 解码 | 87.35 | — |
| `detail_motion` | 编码 | 301.22 | — |
| `detail_motion` | 解码 | 187.18 | — |

`compact` 的常驻后续任务相对首次任务，中位数编码减少约 5.9%，解码减少约 9.2%。这是 C0 同进程测量得到的状态差异，不是 C1 的独立优化收益，也不是最终加速结论。编码样本范围较宽，后续成对比较继续使用交错运行和原始样本，不用单次最好值。

表中首次任务的主值从任务开始计时，不包含工作进程导入时间；括号内另列进程启动至就绪的完整冷态边界。按完整进程边界把编码与解码中位数相加，首次约 123.11 秒；常驻后续任务合计约 111.57 秒。编码和解码并未在同一时刻并行执行，这些和数仅用于描述连续两端处理的量级。

## 4. 热点诊断

以下取 `compact` 常驻后续任务的代表样本；嵌套计时不直接相加。

| 方向 | 总就绪时间 | 帧内时间 | 熵索引 + rANS | 输入/输出 PNG 相关 |
| --- | ---: | ---: | ---: | ---: |
| 编码 | 69.71 | 38.28 | 8.50（约 12.2%） | 输入抽帧 15.23，其中源 PNG 保存 14.86；重建 PNG 14.48 |
| 解码 | 41.86 | 29.32 | 7.59（约 18.1%） | 重建 PNG 12.22 |

66 帧采样的 GPU stream span 显示 P 路径的 `vqgan_generator` 与 `prior` 区间较长，编码和解码都如此；这些 span 可能包含等待，不能当作可相加的 GPU 忙碌时间。Profiler 报告没有捕获 CUDA kernel activity（采样帧的 CUDA event count 均为 0），因此不能据此给出逐 kernel GPU 占比。Profiler 仅用于诊断，没有用于正式速度成绩。

因此下一阶段优先级是：

1. C1 先按完整证据和展示两种输出范围分别衡量 PNG 往返/保存开销；只在同一输出范围内比较加速，并逐帧核对 RGB 摘要。
2. 模型常驻和只读熵表复用继续保留，但要把首次和后续任务分开报告。
3. C2 的原生 rANS 有明确热点，但按当前占比单独替换的总体收益上限有限；GPU 子模块候选应围绕 P 路径和同步开销做小样本开关验证。

## 5. 正确性结果

- 18/18 正式任务的 RGB 与潜变量帧摘要均与 B4 对应记录一致。
- 9/9 正式编码任务的完整 `.glcv` SHA-256 与 B4 码流一致；8 档输入直接与 B4 保存帧逐像素核对，`detail_motion` 另与 A2 保存的同源 RGB 帧完成 250/250 像素一致性核对，并验证 A2 原流至 B4 重打包仅改变容器、神经载荷逐帧相同。
- 9/9 正式解码任务均为独立解码，未读取源媒体，整文件校验通过，逐帧/有序聚合校验通过；另 1 个 66 帧诊断解码也通过相同范围校验。
- 四档参数链和容器 v2 均按 B4 记录核对；没有改变模型、码流格式或算术精度。

C0 只测本机离线编解码与预览；浏览器上传、排队、加载和传输时间没有测量，相关统一字段保持 `null`。结果不能代表网页端等待时间或水声端到端时效。

## 6. 进入 C1 的条件

C0 已提供统一计时字段、冷/热态基线、热点证据和本地证据索引，满足后续 C1 的基线前置条件。C1 是否启动遵循用户后续指示；若启动，仍需保持相同输入、四档参数、成对输出范围和独立解码校验。C0 本身没有声称达到 20% 或 2 倍目标，也没有实施任何加速改动。
