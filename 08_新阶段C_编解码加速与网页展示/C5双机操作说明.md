# C5 双机操作

发送电脑：RTX 4060 Laptop / 8 GB。目标接收电脑：RTX 4070 Laptop / 8 GB。当前只完成本机独立进程与 TCP 联调，真实两台电脑验收待接收机到位。

## 本机入口

- 发送端：`启动C5发送端.cmd` → http://127.0.0.1:8773/
- 接收端：`启动C5接收端.cmd` → http://127.0.0.1:8774/
- C4 也使用 8773，启动 C5 前正常关闭旧 C4 服务，或在端点配置中另选端口。
- 打开、刷新和准备文件不会加载神经模型。显式点击“检查环境”会检查 CUDA 与依赖；“开始发送”才执行编码/解码。
- 停止任务用页面按钮。关闭页面不停止服务；启动控制台 Ctrl+C 会取消未完成任务并清理工作进程。

## 接收机准备

1. 获取仓库 `codex/glc-c` 分支，保留目录结构。
2. 安装兼容的 Python 3.12、PyTorch 2.5.1+cu124 / torchvision 0.20.1+cu124，以及仓库 `04_外部依赖快照/semantic-video-training/requirements-glc.txt` 所列依赖。目标是与发送端环境报告一致；不要直接复制 Windows venv 后假定可迁移。
3. 单独准备 GLC 上游源码（revision `126db25f9c093508cd0c99cee32b53fd60074f9a`）、两份 GLC 权重、FFmpeg 与同目录 FFprobe，以及 native rANS DLL。GPU 驱动应能运行所选 CUDA 构建；以预检结果为准。
4. 把 `runtime.example.json` 复制为 `runtime.local.json`，按本机位置填写五项 runtime 路径。文件路径相对配置文件，不是终端当前目录。历史实验数据无须搬过去。
5. 把 `c5_receiver.example.json` 复制为 `c5_receiver.local.json`。接收端监听 `0.0.0.0`，HTTP 控制端口 8774，TCP 数据端口 8771；任务目录与发送端分开。上述 `.local.json` 不提交 Git。
6. 路径检查：`powershell -NoProfile -ExecutionPolicy Bypass -File .\launch_c5.ps1 -Role receiver -Check`。随后启动接收端，在本机网页点击“检查本机环境”，保存生成的 `preflight_*/environment.json`。
7. 接收端高级设置先保持“严格匹配”。4060 与 4070 的 GPU 名称必然不同；进行这对设备的验证时，显式改选“设备配对诊断”。该模式只允许名称差异，软件、算力、FP32/确定性仍须一致，每条流仍核对 RGB/latent。校验失败不能视为兼容。
8. 同一局域网内，允许接收机程序在 Windows 防火墙的**专用网络**接收入站 8774/8771。不要把端口映射到公网。网页只在各自本机访问，局域网 HTTP 用于带口令的控制调用。

口令由接收端首次启动生成，保存在任务目录 `connection-token.txt`；在本机网页“显示连接口令”复制。口令仅放本地配置，勿随实验报告上传。它用于可信局域网连接识别，HTTP/TCP 没有 TLS 加密。

## 两台电脑上的操作

1. 接收端选择 **最大速度**，保存。展开连接信息并复制连接口令；用 `ipconfig` 查接收机局域网 IPv4 地址。
2. 发送端填写 `http://接收机IPv4:8774` 与口令，点击“保存并检查连接”。
3. 首次用已验证的 8 帧 `.glcv` 检查设备配对，再做至少 66 帧（覆盖 reset32、GOP64）及完整 10 秒任务。发送原视频时可以选择四档画质及前 10 秒、时间区间、完整视频。
4. “准备文件”只上传到发送端本机；页面会显示真实时间轴计划。点击“开始发送”后编码 `.glcv`，通过 TCP 发送，接收端校验完整文件后独立解码。原视频、发送端预览、逐帧侧信息均不传给接收端。
5. 接收电脑在自己的网页查看与下载重建 MP4；发送端显示接收任务完成和校验摘要，不自动把较大的 MP4 返回发送机。
6. 已有码流可以直接上传，或在已结束的发送任务点击“复用码流再发”；新任务不再次编码，接收端会按新预约设置接收并解码。
7. 20/40 kbps 已实现，单位为十进制千比特每秒，对**前向 TCP 应用层帧头 + .glcv 数据**节流。控制 HTTP、ACK、TCP/IP 开销单独记账，不等同于实际水声链路总带宽。最大速度不主动等待。
8. 遵照用户要求，本机不做 20/40 kbps 限速实验。两机到位后也先验证最大速度；限速体验可选，不自动增加矩阵。

接收端修改速率只影响随后预约的任务。四档画质与三档网络速度互相独立。

## 中断、重试与记录

- 传输中断：保留 `.part`，不发布完成码流或可播放 MP4。重新发送创建新任务，当前版本不做字节级断点续传。
- ACK 丢失：接收端先持久保存完整接收状态再 ACK；即使 ACK 丢失，也继续解码。发送端会按接收任务编号查询，避免重复覆盖。
- 接收端失联：发送端不能声称远端已停止。恢复连接后用任务详情里的“查询原接收任务”核实，再决定是否重发。
- 服务重启：未完成任务标记 interrupted，不自动接着跑。若旧 worker 仍存活或身份不确定，会阻止新 GPU 任务。
- 后端缺少 DLL 时，可两端分别手动选 Python 熵后端；这不等于 CPU 神经推理，神经模型仍使用 CUDA。
- 任务目录保存初始参数、状态变更、码流摘要、代码摘要、传输逐块 CSV、编解码计时、进程监督记录及结果。成功任务可下载码流、预览与 JSON；失败任务保留失败日志。

时间采样以实际 PTS 为准，固定输出 25/12.5 fps。区间左闭右开，EOF 不足一帧的尾部向上量化至一帧时长；例如 NOAA 全片为 346 帧/27.68 秒。旋转元数据、无效时间轴及超过 10000 输出帧的范围会明确拒绝。原始 B4 帧数/stride 路径仍保留用于历史复现。

## 可选常驻模式

端点配置 `worker_mode` 默认 `cold`。需要连续处理时，可以改为 `resident` 并重启该服务：模型在首次显式任务时加载，后续任务复用单角色模型。页面底部“资源与运行模式”可在没有未完成任务时释放；取消或失败会退出该 worker，后继任务重新加载。

本机共用一张 8 GB GPU 时维持两个端点都用 cold；已测常驻结果来自一次只运行一个角色。真实两台电脑可各自选择常驻，但先通过冷态配对与显存检查。本次三对测试的独立角色派发耗时降幅中位数为 16.47%，不等于网页端到端提速，未达到或宣称验证 52 秒目标。
