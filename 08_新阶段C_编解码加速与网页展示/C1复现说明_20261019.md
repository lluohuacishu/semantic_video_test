# C1：运行入口与测量口径

日期：2026-10-19。C1 复用原 `NeuralCodec.frame()`、熵编码、确定性 FP32、权重、容器 v2 和四档参数。原 `glc_video_codec.py`、C0 测量入口保持不变，可作为回退和对照。没有训练或新增编译依赖。

## 1. 两种输出模式

| `output_mode` | 交付内容 |
| --- | --- |
| `research` | `.glcv`（编码端）、全部源/重建 PNG、逐帧 PSNR（编码端）、源 RGB/重建 RGB/潜变量摘要、JSON、观看 MP4 |
| `display` | 相同 `.glcv`、逐帧指标与摘要、JSON、观看 MP4，不生成 PNG 中间帧 |

科研模式默认 `png_level: 1`；需要参考压缩级别时设为 `6`。PNG 始终无损，级别只影响 PNG 文件大小和保存成本。实际传输码流仍是 `.glcv`，PNG 和 MP4 均不计入通信包。

输入维持 OpenCV 解码、`INTER_AREA` 缩放、BGR→RGB 和原 `frame_stride` 规则。一次只处理一帧 RGB，FFmpeg 每路最多排队两帧；待写线程和提交者各至多持有一帧。压缩后的神经包暂存在有大小上限的缓冲中，实际 EOF 确认帧数后通过原 `StreamWriter` 发布，避免把视频元数据中的估计帧数当作实际帧数。RGB 整段视频不驻留内存。

预览使用 FFmpeg `rgb24/rawvideo` 标准输入，明确尺寸与帧率，输出可寻址的普通 MP4 文件。依据：[FFmpeg rawvideo](https://ffmpeg.org/ffmpeg-formats.html#rawvideo)、[pipe 协议](https://ffmpeg.org/ffmpeg-protocols.html#pipe)。FFmpeg 参数仍为 `libx264 / fast / CRF16 / yuv420p / +faststart`，与原预览一致。

一组任务只初始化一次模型与熵表。每个任务前后清空 DPB，每段重新建立帧序号、记录和聚合摘要，不缓存任务结果。发送端的 `preset` 必须显式选择 `detail_motion`、`detail`、`motion`、`compact` 之一。可选 `frames` 改变片段长度，其他参数由既有预设确定。运行器直接复用模型已有的掩码缓存，没有新增 GPU 算术优化。

接收配置把 `role` 设为 `decode`，任务 `input` 指向 `.glcv`，不传原媒体。接收器禁用源帧编码模块，使用自己加载的模型，逐帧重建后验证容器完整性和有序聚合摘要。它不接受发送端张量或参考状态。

接收任务的尺寸、帧率、帧数由流头决定；不需要 `preset`。如为实验记录填写 `preset`，它只是元数据，不能改变解码。Python 文件读取审计用于发现本路径的误读，不是操作系统隔离沙箱；实际接收调用链只读取码流和预共享模型资源。

## 3. 常驻接口、状态与取消

- `ResidentRunner.run(task, cancel_event=None, on_event=None)`：串行执行，`threading.Lock` 防止同一运行器并行使用 DPB。
- `cancel_event`：协作式取消，在帧和预览边界生效，不强行中断一次 GPU 内核。失败或取消后清空 DPB，下一个新目录任务可以继续。
- `--jsonl`：同一进程从标准输入逐行读取任务、逐行返回 JSON。该接口是串行请求协议；交互取消使用 Python API。网页队列和取消协议由 C3 整合，C1 不宣称已有网页验收。
- `status.json`：`running` → `preview_pending` → `ready`；异常为 `failed` 或 `cancelled`。预览 MP4 只有写完、FFmpeg 成功退出后才发布正式文件名。
- 失败保留 `failure.json` / `worker_failure.json`、traceback、FFmpeg 日志和半成品。输出目录不可覆盖；恢复使用新的任务 ID 和目录。

## 4. 计时和对照

| 字段 | 含义 |
| --- | --- |
| `codec_acquire_seconds` | 本次模型获取；首次包含权重核对、加载、熵表和 CUDA 初始化相关等待 |
| `bitstream_closed_seconds` | 编码完整码流关闭并发布 |
| `decode_verified_seconds` | 接收端全部重建与聚合校验完成（C1） |
| `evidence_ready_seconds` | 本模式所需码流、校验、指标及证据 JSON 就绪；科研模式包含所有 PNG |
| `offline_view_ready_seconds` | 再包含所有 MP4 完成；不包括浏览器上传、排队和播放加载 |
| `task_timer_origin_perf_counter` | 内层计时的真实起点，用于校准首任务绝对端点 |
| `process_launch_to_evidence_ready_seconds` / `process_launch_to_view_ready_seconds` | 首次任务从父进程启动标记起算，包含配置写入、进程启动、导入及内层计时前准备；后续任务为 `null` |
| `process_launch_to_task_return_seconds` | 同一起点至执行器调用返回，包含预览和任务状态/计时写入 |
| `startup_before_first_task_seconds` | 父进程启动标记至真实内层计时起点；不是纯模型加载时间 |
| `outer_call_wall_seconds` | 无详细函数埋点的执行器外层墙钟复核，含状态/计时文件管理成本 |

C1 预览在逐帧处理期间进行，管道等待已进入任务墙钟；不能将预览与帧处理耗时再次相加。独立验收 PNG、B4 对照和 ffprobe 检查在正式任务计时之外，双方采用相同验证范围。

`run_c1.py` 的参考控制调用原 C0 编解码循环，仅包裹模型获取、输入 RGB 哈希和就绪时刻。展示模式参考仍需原 PNG 路径生成 MP4，随后在计时内删除本任务的 PNG 中间目录；最终保留的交付范围与 C1 展示模式一致。这是为 C1 建立的展示模式控制，不能称为 C0 已测过展示模式。

正式比较关闭 Profiler 和逐模块包装。科研模式按参考 PNG6 → 内存 RGB/原始帧预览 + PNG6 → PNG1 的相邻配置归因；每轮反转或交错顺序。展示模式单列。最终组合直接与参考完整运行比较，不把分项节省相加。连续三任务的常驻策略与三次独立进程另测，首次初始化和进程成本均保留。

**历史计时修正：** `C1_final_20261019/` 的原 46 个正式样本没有记录真实内层起点，旧 `process_launch_to_evidence/view` 字段遗漏内层计时前准备。因此只读汇总将这些旧字段置 `null`；原 `startup_before_first_task_seconds + outer_call_wall_seconds` 可准确恢复“进程计时起点至任务返回”。原始文件不回写。补测目录使用修正后的元数据；两组 `measurement_code/` 和 manifest 保留版本边界，详见 [阶段报告](C1阶段报告_20261019.md)。
