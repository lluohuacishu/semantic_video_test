```powershell
& $py -B "$c\run_c2.py" diagnose --output "$data\C2_new_diagnose" --frames 66 --pairs 1
```

每个视频门槛为两个编码任务（Python/native）和四个独立接收端交叉任务。源 RGB、重建 RGB、潜变量、载荷、预览帧数/尺寸/帧率均与冻结 B4 对照；同长度新旧完整流还必须逐字节一致。66 帧跨越 GOP64 和 reset32。任一步失败，停止该候选，不放宽一致性要求。

门槛通过后才运行选定档位的完整视频配对：

```powershell
& $py -B "$c\run_c2_paired.py" paired --preset compact --pairs 3 --output "$data\C2_new_compact_pairs" --native-library $dll --prior-gate "$data\C2_new_gate66"
```

各端先用 Python/native 各完成一次 8 帧预热，后续三对交替 AB/BA。正式配对不开热点埋点，双方保留相同心跳与进度包装。`paired_summary.json` 给出各端及同 pair 两端之和的分布；这不是收发网络或浏览器端到端计时。`--preset` 支持四档，但一条命令只跑指定档位，避免隐藏长矩阵。其他档位和独立素材的缺口须如实列出。

## 监督与停止

2026-10-19 的暂停已于 10 月 20 日按用户指令恢复。旧第二素材完整配对 r1 在写心跳时失败，原目录保留；新批次三对已完成。日志重试通过真实 Windows 文件锁测试，修复后的新视频任务已正常结束。`inspect` 已补强不确定查询与不可读/损坏心跳的处理，恢复前也用系统进程列表核实。

最终组合入口为 `run_c2_combined.py`：先执行 `gate8 --native-library <r3 DLL> --prior-gate <已通过的主片 gate66> --output <新门槛目录>`；门槛通过后，才执行 `paired --pairs 3 --native-library <同一 DLL> --prior-gate <新的 combined gate8> --output <新配对目录>`。该分支比较原 legacy Python 与 C1+native，不沿用 C1 对 native 的收益标签。今日门槛为 `C2_combined_gate8_20261020_r2`；r1 是已保留的输入编排失败现场。正式接收端现在读取本批 `encode_1_python/stream.glcv`，不会在短任务中误用完整 B4 码流。

每个进程目录保存 `process.json`（监督器与子 PID、创建时间、心跳、返回码和耗时）、`heartbeat.json`（工作进程状态和最后完成帧）、`worker.log`、`fatal.log`，失败时另有 `exception.json`。正常任务另保留 C1 的状态/失败/预览子进程日志。

准备断电时，在正在运行的实验根目录创建 `STOP_REQUESTED`：

```powershell
New-Item -ItemType File -Path "$data\<正在运行的目录>\STOP_REQUESTED"
& $py -B "$c\run_c2.py" inspect --output "$data\<正在运行的目录>"
```

工作进程在下一帧/预览边界取消并清空 DPB、关闭预览；后续任务不再启动。监督器等待最多 60 秒，超时只终止其正在持有的子进程树，并记录强制终止。未完成样本排除、日志保留；成功的先前任务仍做离线校验。

`inspect` 不启动 GPU，也不修改原始记录。PID 与创建时间同时匹配才视为同一进程：

- `running`：子进程与监督器仍在。心跳是存活证据，不证明持续取得进度；另查最后完成帧与时间。
- `orphan_running`：子进程仍在、原监督器已不在。先核实旧进程，不能同时派发新的 GPU 任务。
- `liveness_unknown`：查询失败、创建时间缺失、心跳不可读/损坏等情况导致无法确认。即使已有退出码也不能覆盖不确定的实际 worker，恢复工具拒绝继续。
- `interrupted_exit_unknown`：没有最终退出码且原子进程已消失。保留未知原因，不能宣称崩溃原因已查明。
- `failed` / `cancelled` / `completed`：监督器已记录终态。`completed` 只表示进程返回 0；阶段还需要逐任务验证和 `gate.json` 或完整配对汇总。

这些机制不能保证捕获断电、OS 强制结束或应用崩溃的最终事件。C1 历史两次中断原因仍未知。重新开始必须使用新目录；不覆盖旧码流、状态、日志或源码快照。

若监督器消失而某些任务已完成，可以在确认原进程全部退出后，运行 `recover_c2.py --experiment '<实验目录>' --report '<新的恢复记录.json>'`。它按 manifest 选择 B4 或第二素材同片参考，只对具有完整终态元数据的任务做离线校验，不启动推理，不填造未知退出码；未完成任务列入 excluded。恢复报告使用新文件，原始进程记录不改。

## 完整视频冷启动与离线汇总

`run_c2_cold.py --native-library <r3 DLL> --prior-gate <combined gate8> --output <新目录>` 只做一对完整 compact：原 legacy Python 和 C1+native 的编码、解码各用一个新进程，共四个，先编码再独立解码，不预热。接收端读取本次 Python 编码结果，四份输出均需通过 B4。

冷态端点由外部调度 `perf_counter` 与任务真实起点相接，包含监督/配置准备、导入和任务内模型加载。模型加载不再次叠加；任务后 GPU 快照、进程清理与离线参考校验不属于“预览已就绪”等待。操作系统文件缓存不清空；单对仅作成本示例，不能声称三次重复或稳定冷态加速比。

所有实验结束后可运行 `audit_c2.py --data-root <C 数据目录> --checks <最新通过的检查目录> --output <汇总 JSON>`，只读核对原输入、measurement_code、DLL、状态、结果/码流摘要、配对和中位数；不会运行 GPU 或重写实验原件。脚本列明本次固定证据目录；若缺少尚未完成的目录，会拒绝输出完整汇总。C2 原生实现仍需显式 `backend=native` 和对应 DLL，默认 Python 参考保持可用。

性能汇总只纳入同一实验根目录、同一 pair 的 Python/native 编码和解码四个完整有效任务。跨断电留下的不完整 pair 可保留为兼容性证据，下一次重新测该完整 pair；不能用旧日 Python 时间配新日 native 时间。已完成的完整实验无需重跑。多批次汇总必须保留根目录和 pair 身份，不能因重复数字 ID 覆盖旧记录。

## 构建可追溯性

`build_c2_native.py` 校验固定上游头文件 SHA-256，使用现有 `C:/mingw64/bin/gcc.exe`，将源码复制到 ASCII 临时目录构建，再用 Python 回拷 DLL。`-B` 指向同套工具的 bin 子程序；不修改机器全局 PATH 或安装依赖。失败目录保留返回码和输出。

每次实验的 `manifest.json` 包含源码 SHA-256、模型路径相关源码、输入 SHA-256、GPU/电源概况和 DLL 构建记录；`measurement_code` 保存对应源码。不同版本使用新目录，不用较新的工作树解释旧计时。
