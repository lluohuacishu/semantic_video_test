# GLC 网页界面

网页调用本项目已有的 GLC 编码、文件传输和独立解码脚本，使用 `.venv-glc` 环境。原来的语义分割和图片编码页面保留。

## 启动与操作

1. 在项目目录双击 `run_glc_demo.cmd`，保持启动窗口运行。浏览器会打开 <http://127.0.0.1:8770/>；已启动时重复双击会打开现有页面。
2. 拖入一个视频，或点击上传区域选择文件。支持 MP4、AVI、MOV、MKV、WebM、M4V，大小上限 1 GiB；能否读取其中的具体编码取决于本机解码器。
3. 第一次建议使用 `1280 px / 50 帧 / q=63 / 20 kbps`。这只处理一个短片段，不是默认处理整段视频。
4. 点击“开始实验”，依次等待编码、文件传输、独立解码和核验。720p 片段通常需要几十秒到几分钟，不能实时播放传输。
5. 完成后点击“同步播放”，对比输入片段和接收端还原。下载区域可保存还原视频、并排对比视频、真实码流及实验数据。

“最近实验”可以重新打开结果。修改参数后点击“按当前参数重新运行”，会复用保留的原视频，建立一条新记录，不覆盖之前的结果。多个任务按顺序处理，避免同时占用显存。

开始编码后，刷新网页不会停止后台任务。“停止任务”会结束本次处理进程，保留已上传的原视频；上传未完成时停止，需要重新选择文件。关闭服务前建议先停止任务，再在启动窗口按 Ctrl+C。服务重启后，完成的历史记录仍可打开，未完成的记录会标记为中断。

界面只监听本机 127.0.0.1，不向公网提供服务，也不需要安装额外的 Web 依赖。

## 参数含义

| 参数 | 作用 |
| --- | --- |
| 重建质量 q | 0～63，越大通常越清晰、码流越大；使用官方预训练模型，不会重新训练 |
| 最大宽度 | 按比例缩小输入，不放大低清素材；1280 对应常见横向 720p 输入 |
| 最多处理帧数 | 限制本次片段长度；例如 5 FPS 的 50 帧是 10 秒，25 FPS 的 50 帧是 2 秒 |
| 文件传输速度 | TCP 应用层限速，默认 20 kbps；变慢只延长传输等待，不改变画质 |
| 起始帧 | 从 0 开始计数，便于选取同一视频的其他片段 |
| I 帧间隔 | 周期性安排独立编码帧；默认 32，其他帧采用时间参考 |
| 参考重置间隔 | 官方视频模型的周期参考特征重置参数，默认 32；0 表示不周期重置 |

目前保留源视频的名义帧率，只处理画面，不处理音频或可变帧率时间戳。8 GB 显存建议先用 720p；1080p 可尝试，但不同画面和其他程序的显存占用会影响能否完成。

## 页面指标与文件

- **实际码流大小**：真正发送的 `.glcv` 文件大小，包括本地容器头与校验。下载的 MP4 是观看副本，不是实际发送数据。
- **压缩后视频码率**：`.glcv` 文件字节数 × 8 ÷ 片段播放时长。可以高于 20 kbps，因为允许以 20 kbps 多花时间传完文件。
- **文件传输耗时**：真实本机 TCP 发送与接收耗时。应用层统计包含传输头，不包含 TCP/IP 和底层协议开销。
- **平均 PSNR**：输入与浮点重建帧的像素差异指标。它不能单独说明人物姿态、小鱼等语义内容保持得好不好。
- **编码／解码处理时间**：逐帧网络计算、熵编解码和校验耗时，不含模型加载、抽帧和 MP4 预览制作，所以会小于总等待时间。
- **接收校验通过**：接收文件、两端重建帧和参考特征通过核对；独立解码进程没有读取原视频。这不表示还原视频与原视频无损一致。

结果位于 `runs/glc_console/<任务 ID>/`：

```text
source.mp4 / source.avi       保留的输入视频，重跑时复用
job.json                     参数、状态和摘要
job.log                      编解码进程日志
progress.json                最近一次进度
result/summary.json          完整实验记录
result/q63/sender.glcv       编码生成的真实码流（目录随 q 改变）
result/q63/received.glcv     实际收到的码流
result/q63/receiver/         独立解码帧、观看视频及解码记录
result/q63/frames.csv        逐帧大小、PSNR、编码与解码时间
```

输入、权重和实验产物不随 Git 上传。重复实验会累积文件，尤其是逐帧 PNG；清理时先停止服务，再删除自己不需要的任务目录。网页不自动清理。

## 本机验证（2026-10-04）

通过网页上传导师提供的 `test5_5fps_reconstructed.avi`，使用 1280×720、5 FPS、8 帧、q=63、20 kbps 完成编码、TCP 传输、独立解码及一致性校验：

| 项目 | 结果 |
| --- | ---: |
| 片段时长 | 1.6 秒 |
| 实际码流 | 16,057 B |
| 压缩后视频码率 | 80.285 kbps |
| 文件传输耗时 | 6.468 秒 |
| 平均 PSNR | 34.23 dB |
| 编码／解码逐帧处理 | 17.20 / 12.06 秒 |
| 编码峰值张量显存 | 约 3.04 GiB |

这份 AVI 本身已经是重建视频。以上用于检验网页和流程，不是从原始拍摄素材出发的正式压缩评测，也不代表所有水下视频的质量。

另通过网页上传 MP4，在文件传输途中停止，再复用保留的输入重跑 1280×720、4 帧、q=63、40 kbps。实际码流 10,148 B，传输 2.062 秒，平均 PSNR 34.04 dB，独立解码校验通过。该 MP4 来自上述 AVI 的输入预览，只用于格式与操作检查，不是第二份独立评测素材。

网页上传、取消、重跑、历史恢复、分页、断开连接及媒体 Range 请求的 11 项测试通过；已有熵编码、容器与文件传输的 15 项测试也通过。浏览器中检查了同步播放、回到开头、下载码流和服务重启后的结果恢复，下载文件与编码产物的 SHA-256 相同。

## 当前边界与下一步

本次增加了网页和任务管理，未训练新模型，也未改变 GLC 网络。使用官方 GLC 权重，真实熵编码与 `.glcv` 容器由本项目补充；目前只验证相同 PyTorch／GPU 环境下的独立解码。

建议接下来固定几段水下素材，对 q=0、31、63 做相同分辨率和帧数的比较，同时记录实际文件大小、传输时间、画质和目标语义是否保留。先找出人物、小鱼、运动物体的具体失真，再决定如何加入水下语义约束。当前未加入水下分割条件或物理信道，不能仅凭网页跑通就称为完整的水下语义通信系统。
