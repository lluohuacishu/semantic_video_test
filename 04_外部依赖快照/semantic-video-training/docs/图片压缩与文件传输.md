# 图片压缩与文件传输

## 这一步解决什么

先跑通图片的“编码成文件 → 限速发送 → 接收校验 → 解码还原”。带宽要求按文件发送速度理解：20 kbps 约为 2500 字节／秒，40 kbps 约为 5000 字节／秒。文件可以慢慢传完，不要求传输耗时短于视频播放时长。

图片链路使用 [CompressAI 官方实现](https://github.com/InterDigitalInc/CompressAI)的 `bmshj2018-hyperprior` 通用预训练模型，模型说明见[官方模型库](https://interdigitalinc.github.io/CompressAI/zoo.html)。没有重新训练压缩器，也没有接入 GLC-Video。已有 SUIM SegFormer-B0 负责检查还原后分割是否发生变化，暂时不参与压缩器的损失函数或码率分配。

## 实际流程

1. 按原尺寸读取 RGB 图片，右边／下边补齐到 64 的倍数。
2. 神经分析变换得到潜变量 `y`；超先验网络得到辅助潜变量 `z`。
3. 量化并用 rANS 熵编码生成两条真实字节流，保存成 `.svic` 文件。
4. 发送端通过 TCP 发送该文件，按照累计发送字节数控制速度。
5. 接收端核对长度和 SHA-256，完整接收后才发布 `received.svic`。
6. 接收端仅根据文件和本地模型解码，裁掉补边，保存原尺寸 PNG。
7. 在原图和还原图上运行同一份 SegFormer，记录画质和预测变化。

`.svic` 是本项目给 CompressAI 字节流加上的封装，包含原图尺寸、质量档位、潜变量形状、模型版本及校验记录。它不是通用图片格式，也不等同于 GLC 码流。模型权重预先放在收发两端，首次分发模型的成本没有计入每张图片的文件大小。

## 前台操作

本机环境已经准备好，无需再次安装或训练。

1. 双击项目根目录 `run_image_codec_demo.cmd`，页面地址是 `http://127.0.0.1:8769/`。
2. 等右上角分割模型就绪。保持“图片压缩 · TCP 文件传输”模式。
3. 先选质量 3、限速 20 kbps，拖入一张图片或点击选择文件。
4. 等进度走过编码、TCP 传输和解码，查看原图与还原图。
5. 切换“前后类别”，左边是原图分割，右边是还原图分割。叠加结果显示还原图上的预测。
6. 修改质量或限速，点击“用当前参数重新处理”。每次运行创建新记录，旧结果保留。

质量 1 通常文件更小、纹理损失更多；质量 5 通常保留更多细节、文件更大。质量档位决定压缩模型，20／40 kbps 决定文件发送速度，两者独立。

图片支持 JPG、JPEG、PNG、WebP、BMP，最长边不超过 4096，最多 4,194,304 像素。720p 和 1080p 均在范围内。图片先转为 RGB；不是无损压缩。

“语义检查输入边长”只影响分割检查，不会缩小实际编码图片。默认 256 与 SegFormer 训练尺寸一致。提高到 384 或 512 不保证更准确。

视频压缩与传输尚未接入。选择“语义分割 · 图片／视频”仍可使用原来的视频逐帧分割功能。

## 指标怎么看

| 页面数据 | 含义 |
| --- | --- |
| 实际压缩文件 | `.svic` 总字节数，包含封装头与两条码流 |
| bpp | 文件字节数 × 8 ÷ 原图像素数 |
| PSNR | 全图 8-bit RGB 像素误差转换的 dB 值 |
| SSIM | `pytorch-msssim` 的 7×7 Gaussian 单尺度结构相似度，不是 MS-SSIM |
| 实际平均发送 | 发送方向的应用层文件＋传输头字节数 × 8 ÷ 实际传输秒数 |
| 编码／解码计算 | CPU 网络及熵编解码耗时，不包含模型加载、图片读写和质量检查 |
| 前后类别一致 | 同一分割模型在原图／还原图上给出相同类别的像素比例 |

预测一致不代表预测正确。原模型把珊瑚分成沉船，还原后仍分成沉船，也会得到高一致性。带人工标签的 SUIM 验证实验另外报告相对真值的 mIoU。

“压缩比”若按未压缩 RGB 计算，分母基准是宽 × 高 × 3 字节，不是源 JPG／PNG 文件大小。ZIP 包含预览图、两份码流和报告，比通信文件大；还原 PNG 也不是通信码量。

限速统计包括传输协议的应用层头，但不包括 TCP/IP 包头、链路层开销和反向确认。它是本机应用层限速测试，不能直接当作实际水声链路的净容量或误码实验。程序按累计时间发送 1024 字节的小块，没有初始整文件突发。

## 本机结果（2026-10-01 至 10-02）

### 720p 图片的真实收发

使用同一张 1280×720 的潜水员与鱼类画面，质量 3，原尺寸编码：

| 项目 | 结果 |
| --- | ---: |
| `.svic` 文件 | 10,155 字节，约 9.9 KiB |
| 其中神经码流 | 9,748 字节 |
| bpp（含封装头） | 0.08815 |
| PSNR／SSIM | 39.51 dB／0.9742 |
| 20 kbps 实际发送 | 4.119 秒，平均 19.907 kbps |
| 40 kbps 实际发送 | 2.066 秒，平均 39.694 kbps |
| 原图／还原图预测一致 | 97.94% |
| 接收文件校验 | 通过 |

20 kbps 对照包含 95 字节应用层传输头，共发送 10,250 字节；理论最短时间 4.10 秒。传输耗时不包括神经编解码。首轮编码约 460 ms、解码约 428 ms；这些是单次本机记录，不是跨硬件速度结论。

记录位于 `runs/image_codec_console/830fa15718da4414ab9d21e4a89f4b02/` 和 `runs/image_codec_console/697a3d778a1243028afce4665ff8a6e7/`。实验产物没有纳入 Git。

从原有 297 张验证名单等间隔选 6 张，在相同原图上测试 q1／q3／q5。下面的文件大小、bpp、PSNR 和 SSIM 是逐图等权平均；不是全部验证集或测试集成绩。

| 质量 | 平均文件字节数 | 平均 bpp | PSNR | SSIM | 还原图分割 mIoU |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 5,067 | 0.1083 | 30.17 dB | 0.7726 | 61.00% |
| 3 | 10,115 | 0.2290 | 33.49 dB | 0.8595 | 55.30% |

## 分开运行编码端与接收端

在项目根目录执行以下命令。每个输出路径应是新文件。

先编码：

```bat
.venv-segformer\Scripts\python.exe scripts\image_codec.py encode --input "你的图片.jpg" --output runs\my_image\encoded.svic --quality 3
```

在第一个终端启动一次性接收端：

```bat
.venv-segformer\Scripts\python.exe scripts\file_transfer.py receive --host 127.0.0.1 --port 8771 --output runs\my_image\received.svic
```

在第二个终端发送，收完后两端自动退出：

```bat
.venv-segformer\Scripts\python.exe scripts\file_transfer.py send --host 127.0.0.1 --port 8771 --input runs\my_image\encoded.svic --kbps 20
```

随后独立解码：

```bat
.venv-segformer\Scripts\python.exe scripts\image_codec.py decode --input runs\my_image\received.svic --output runs\my_image\reconstructed.png
```

本机已验证编码和解码分别在新进程执行，解码图与 CPU 模型直接重建逐像素一致。发送、接收和解码三个独立进程也已跑通，收到的文件与前台码流一致，还原像素与前台输出相同；记录在 `runs/image_codec_cli_tcp_20261002_verified/verification.json`。接收侧不需要源图片。当前只完成本机环境验证；迁移到另一台机器应使用相同版本环境与权重，再做交叉编解码检查。

## 环境与来源

复用 `.venv-segformer`，原 `.venv` 保留。当前为 Python 3.13.7、PyTorch 2.12.0 + CUDA 12.6、NumPy 2.5.2。图片编解码使用 CPU，SegFormer 分割可用 RTX 4060 Laptop GPU。

CompressAI 稳定版的 NumPy 依赖与当前环境不兼容，因此使用官方仓库的固定开发版提交 `1c9e3eee83a8f4c8162d38b52f78f5b0c40de175`（`1.2.9.dev0`），没有降低原环境的 PyTorch 或 NumPy 版本。

- 源码来自 `github.com/InterDigitalInc/CompressAI`。
- q1／q3／q5 权重地址来自该提交的 `compressai/zoo/image.py`，实际下载域名是 `compressai.s3.amazonaws.com`。
- 额外 Python 包使用 PyPI 官方索引 `https://pypi.org/simple`，版本固定在 `requirements-image-codec.txt`。
- Windows 使用本机已有的 `C:\mingw64\bin\g++.exe` 编译 rANS 与概率表扩展，只调整构建配置，没有更改压缩算法。
- 来源、实际下载地址、大小与 SHA-256 保存在权重目录的 `provenance.json`；本地构建记录在 `tools/image-codec-build.json`。来源核对与指纹校验分别解决来源和完整性问题。
- 权重仅用 `torch.load(..., weights_only=True)` 加载，演示阶段不联网下载。

重新准备图片编码环境时先完成项目的 SegFormer 环境，再运行 `setup_image_codec.cmd`。如果编译器位置不同，可执行 `setup_image_codec.cmd --compiler-dir "编译器的 bin 目录"`。这个入口需要已经安装的 MinGW，不会自动下载安装编译器。

实测发现 GPU 编码后交给 CPU 解码，预测概率的浮点差异会让熵解码失步，出现严重画面损坏。因此当前码流要求 CPU 编解码，并在文件头记录后端；代码明确拒绝 CUDA 图片编码。分割不受此限制。后续加速时需解决概率计算一致性，不能直接把编码器改回 GPU。

## 文件与检查

每次成功任务保留上传源文件，`result/` 下保存：

- `encoded.svic`、`received.svic`：发送文件与接收副本。
- `input.png`、`reconstructed.png`：原图与实际解码图片。
- `semantic_before.png`、`prediction_color.png`：压缩前后的分割结果。
- `prediction_index.png`、`overlay.png`：还原图类别编号与叠加预览。
- `transfer.csv`、`summary.json`：传输进度及参数、耗时、画质记录。
- `results.zip`：用于查看的结果合集，不作为传输码量。

中断不会把不完整文件标成已接收。接收中的 `.part` 文件保留在本次任务目录；完成文件不覆盖已有文件。容器读取会检查尺寸、码流长度、截断、额外尾部字节和内容校验。

完整单元检查命令：

```bat
.venv-segformer\Scripts\python.exe -m unittest discover -s tests -v
.venv-segformer\Scripts\python.exe -m pip check
```

本机 36 项检查通过，依赖检查无冲突。页面文件选择、参数重跑、压缩文件下载和 ZIP 完整性已检查；在真实 TCP 传输中点击停止后，不会生成完整接收文件或还原图片。

下一阶段可先做离线视频的抽帧、编码、打包传输和重建。逐帧图片编码适合作为对照，但没有利用时序冗余；进一步降低文件大小，需要真正的帧间神经编码或其他视频编码模型。语义损失和重要区域码率分配应在可验证的码流基础上加入。
