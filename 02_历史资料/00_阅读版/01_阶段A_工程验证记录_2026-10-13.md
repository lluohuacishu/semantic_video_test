## 6. 完整文件与初始化协议

本工程的 `video.mlvcv` 使用自定义 `MLVCV001` 容器，内部每个帧包由上游真实 rANS 熵编码生成，容器本身不是微软标准视频格式。

文件包含版本标记、协议头长度、JSON 协议、逐帧包长度、逐帧包数据。协议记录分辨率、padding、fps、帧数、GOP、模型哈希、质量参数、frame-adaptor 索引、初始化方式、每个帧包的长度和哈希。没有把首帧图像或接收端所需状态放在未计费的旁路文件里。

主实验启用 DMCI I 帧：第 0、32 帧是 I 帧，其余 48 帧是 P 帧。I 帧解码重建用于初始化时序参考，接收端不读取发送端原帧。

另外验证了官方 `use_i_frame_model=false` 对应的共享灰色参考模式：初始 YUV 三通道都是 0.5，首个实际视频帧仍作为 P 帧真实编码。它无需原始首帧，不应仅凭配置中的 `false` 判定缺少完整首帧码流。灰色模式 4 帧验证结果：[verification.json](<../../01_主工程/runs/smoke_gray_q0/verification.json>)。

解码 CLI 只有文件、共享模型权重和输出目录。它在新进程中从空 DPB 开始，媒体 / 状态文件读取审计会拒绝访问共享权重之外的原视频、PNG、NPY 等数据。四个主质量点的接收端审计只观察到两份共享权重的读取。

共享权重属于双方预部署资源，不逐视频发送。若实际系统下发微调模型，必须另算权重更新的传输开销。

## 7. 独立解码验收

每个主质量点都分别启动编码、解码、验证进程，不把 Python 内存中的参考状态交给解码器。

核对内容包含每一帧的 uint8 RGB 像素哈希、浮点参考重建哈希、浮点时序特征哈希；不只检查“文件能打开”。四个质量点全部通过，共 200 帧。

更新后的微调权重还完成 4 帧真实文件往返，并通过同样的像素及状态检查。该 4 帧是接口兼容性测试，缩放后与训练中心裁剪不同，不作为微调提升或独立测试集证据。

损坏文件检查：截断帧包、改动末尾数据、提供错误共享权重，均被拒绝解码。见 [result.json](<../../01_主工程/runs/container_failure_checks/result.json>)。

当前验证范围是同一台 GPU、相同 FP32 和确定性配置下的不同进程。没有测试跨 GPU、CPU 或不同精度的解码一致性，不能据此声称达到 MLVC 论文的跨平台部署指标。

## 8. 统一指标与统计口径

- 计入完整文件所有字节：I 帧、P 帧、必要协议和容器；不计日志、重建 PNG 或额外预览 MP4。
- GLC 为已有 `.glcv` 完整文件，MLVC 为 `.mlvcv`，H.265 为可独立播放的 MP4。必要全局 codec 信息计入文件大小。
- RGB PSNR 主列使用所有像素的总体 MSE，再计算 PSNR。另存逐帧 PSNR 平均值，不能把两者混用。
- MS-SSIM 对 RGB 三通道计算，使用本次固定上游 `src/metrics/msssim.py`，范围 0～1，最后取帧均值。
- 三种方法都针对同一组 uint8 RGB 参考图及最终重建 RGB PNG。
- GLC 内部输入为归一化 RGB，MLVC 为 BT.709 浮点 YUV420，H.265 为 BT.709 8-bit limited-range YUV420。评价统一，内部编码域尚未统一。
- 所有主路径使用 GOP 32。H.265 使用 `libx265 medium + zerolatency`，关闭 B 帧和场景切换，实际验证 2I+48P。
- H.265 的 CRF 数值与 MLVC / GLC 的 q 索引不可互相对应；比较时应使用真实字节或 kbps。

20 kbps 采用十进制 20,000 bit/s：`T = file_bytes * 8 / 20000`。视频平均压缩码率是 `file_bytes * 8 / 10 / 1000` kbps。这里的传输时间是理论值，不含纠错、协议、重传或链路波动；没有把理论值写成实际水声传输测量。

## 14. 遇到的问题、处理与保留限制

### 14.1 Windows C++ const 类型

官方 `PyWrapper.h` 的 `auto name = strrchr(...)` 在本机 MinGW 下推导为可写字符指针，随后赋值 `const char*` 报错。改为 `const char* name` 后构建成功。保留上游 `-Wall -Werror`，没有放宽编译检查，也未修改 rANS 编码算法。补丁：[windows_entropy_const.patch](<../../01_主工程/audit/windows_entropy_const.patch>)。官方 7 项熵编码测试全部通过。

### 14.2 I 帧官方下载

OneDrive share API 返回 401，公开分享页 TLS 访问失败，候选 MLVC blob 地址返回 404。已记录，采用公开镜像保持工程推进。后续继续核对官方原件；若哈希不同，先核查来源与参数，不能悄悄换权重后混用旧曲线。

### 14.3 微调 checkpoint 元数据

第一轮训练成功，但保存的元数据包含 Torch 的 `TorchVersion` 类型，上游 `weights_only=True` 的安全加载拒绝该对象。现已把版本保存为普通字符串，重新训练并保存到 `_v2` 目录，真实编解码也通过。没有改成 `weights_only=False`。原失败日志保留在 `audit/phase_a_commands/probe_encode.log`，没有覆盖失败结果。

### 14.4 数据与公平性

当前只有一段来源未核实的重建视频；已完成普通画质比较，没有真实分割标注，没有鱼 / 潜水员 IoU、F1 或时序语义稳定性测量。各编码器内部色彩域不同，而且 H.265 使用 P 帧低延时模式。正式论文对照还需补共同预处理路径、匹配真实预算，以及允许 B 帧的离线 H.265 设置。

## 15. 现在能得出的结论

1. MLVC-S 工程可运行，能够生成包含完整首帧信息的真实文件，并在独立进程解码；它值得继续作为主候选。
2. 8GB 显存不是当前小配置的瓶颈，后续可以开展有控制的预训练微调，而无需从头复刻官方训练日程。
3. GLC 仍有竞争力。尤其在本样本上，其 MS-SSIM 较高；PSNR 和 MS-SSIM 的排序不同，单个像素指标不能代替语义效果。
4. 没有任何已完成实验能证明 SegFormer 或 ROI 带来的增益。本轮结果只建立普通源编码基线。
5. 当前的系统边界仍是数字视频源编码与共享模型解码。20 kbps 理论时间换算不等于完成水声链路实验或 JSCC。

## 16. 下一步的具体推进顺序

### 步骤 A-补充：补齐数据与公平对照

- 获取至少 2～3 段来源清楚、彼此独立的连续水下视频，优先覆盖潜水员、鱼群及不同背景运动；保存来源、许可、SHA256、fps、分辨率和采样规则。
- 当前视频继续留作工程 smoke test。不能同时用同一来源的 1 fps / 5 fps 版本充当训练和独立测试集。
- 按视频来源划分训练、验证、测试，记录 manifest；同视频裁剪和相邻帧不得跨集合。
- 在共同 RGB 参考基础上，增加一套统一 BT.709 / chroma 处理实验；说明量化精度差别。GLC 若需要预处理，在新适配器中进行，保留历史实验。
- 新增允许 B 帧的 H.265 离线设置，固定 GOP 和画质搜索方法；保持当前 P-only 设置作为另一个可复现实验。
- 用真实文件大小搜索质量参数，围绕如 25KB、40KB、60KB、90KB 或明确的传输时长预算匹配，而非直接对齐 q / CRF。
- 核对官方 I 帧原件；压缩容器开销优化使用新版本协议并复验，避免变更统计口径。

### 步骤 B：冻结 SegFormer 并建立可信语义评价

- 先在原始 RGB 参考图和各重建图上运行已有 SegFormer，仅做推理，不立即改编码器。
- 为验证与测试视频选定分布均匀、含遮挡 / 运动 / 低对比度的帧，建立人工分割标注，优先潜水员和鱼类别。
- 固定类别映射、输入缩放、归一化、ignore label、类别缺失时的 IoU 规则，保存评测配置。
- 同时报告参考图上分割性能和重建图上性能；前者衡量教师本身，后者衡量通信后任务结果。
- 训练所用 SegFormer 与评价最好有人工标注或独立模型支撑，避免只优化教师自己的偏差。
- 当前独立 SUIM 图像可以帮助训练分割器，不能替代连续视频数据，也不能证明跨帧稳定性。

### 步骤 C：普通率失真微调与 ROI 加权

- 先用新的训练视频建立普通 `R+λD` 微调基线，再与 ROI 微调保持同初始化、视频集合、更新次数、随机种子和质量采样预算。
- 提前生成水下目标 mask，保存版本和可靠性筛选信息。GT 优先，伪标签需明确置信度及拒绝策略。
- 优先复用官方 `loss_total_rdc_psnr_roi_per_pixel`，检查其辅助分割模型初始化接口，适配预计算 mask。
- 用有目标 / 无目标的实样本检查 mask 对齐、权重归一化、目标像素相对于背景的梯度权重及空 mask 行为。
- 从一个小配置逐级测峰值；开始记录多帧反向的显存和吞吐，需要时再开启混合精度 / checkpointing。
- 每个训练版本都用真实文件编码和独立解码来评价，不能只报告训练估计 bpp。

### 步骤 D：SegFormer 任务损失

- ROI 阶段稳定后，再加入 `R+λD+λ_S L_seg`。SegFormer 参数冻结，重建图经过 SegFormer 的分支仍必须保留梯度。
- 参考图教师伪标签分支可以无梯度；重建图任务损失分支不能整体包在 `torch.no_grad()` 内。
- 调节 λ_S 时同时观察目标 IoU、整体 RGB 画质、非目标区域代价和帧间稳定性，防止只产生教师偏好的纹理。
- 比较普通 MLVC-S、普通微调、ROI、ROI+任务损失，并保留 GLC 作为基线或备选。结果若不支持主假设，应分析失败条件。

### 步骤 E：加入实际传输与信道

- 先复用现有文件限速传输基础，保存发送 / 接收文件哈希和实际耗时；20 kbps 链路时间与视频播放时间分别记录。
- 再引入分包、误码 / 丢包、纠错 / 重传与重同步。重要 I 帧及关键语义信息的保护要计入发送成本。
- 报告干净接收、不同信道条件、同实际发送预算下的任务结果。在此之前避免将源编码实验写成完整水声联合源信道系统。
