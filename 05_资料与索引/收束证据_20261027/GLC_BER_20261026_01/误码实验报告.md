# GLC 误码实验报告

日期：2026-10-26。结论：当前本地 GLC 编解码链路对残余比特错误敏感，不能依靠模型自行纠错。本次实际损坏的 161 个压缩载荷样本全部无法完整解码；其中 48 次只改了一个比特。这个结论针对本地 GLC 模型、原生 rANS 实现和 GLCV 封装组合，并非所有 GLC 实现和所有视频的普遍保证。

## 测试对象与信道

- 真实码流 15,049 B（120,392 bit），其中压缩 z/y 载荷 13,717 B。源文件 SHA-256：`6092d1b0b703d01e452e0c10d9c31429e43b48eaa41bcd2d9696656c39c78370`。
- 640×360，12.5 fps，66 帧，5.28 秒，q=0，GOP=64，reset_interval=32；第 1、65 帧是 I 帧，帧号从 1 开始。
- RTX 4060 Laptop、FP32、TF32 关闭；实际解码使用 `NativeGaussianRans`。头部中的 `python-byte-rans-gaussian128-v1` 是兼容的码流格式标识，不代表本次使用 Python 熵解码。
- 这里的 BER 是进入文件/解码器的**残余误码率**。独立试验按二项分布抽取翻位数量，再无放回抽取比特位置，等价于二元对称信道。未模拟调制、物理链路、丢包或 TCP 重传。
- 另测单比特翻转，以及连续翻转 8、32、128 bit 的突发错误。随机种子和全部位置已保存。

## 1. 正常入口：整文件校验

每档 1,000 次，总计 6,000 次。将翻位后的整文件交给现有 `read_stream`。没有修改校验逻辑。

| 设定 BER | 通过校验 | 实测通过率 | 理论整文件无翻位概率 |
|---|---:|---:|---:|
| 0 | 1000/1000 | 100.0% | 100.0000% |
| 1e-07 | 991/1000 | 99.1% | 98.8033% |
| 1e-06 | 888/1000 | 88.8% | 88.6573% |
| 1e-05 | 326/1000 | 32.6% | 30.0014% |
| 0.0001 | 0/1000 | 0.0% | 0.0006% |
| 0.001 | 0/1000 | 0.0% | 0.0000% |

所有通过的样本都恰好没有发生翻位，所有实际改动的样本都因 `GLC file checksum failed.` 被拒收。因此这个表反映的是文件完好概率及校验表现，**不是模型在带错输入下的容错成功率**。有限样本下的 0/1000 不代表数学概率严格为零；置信区间见 `strict_summary.json`。

对于 N bit 文件、独立残余 BER=p，整文件无错概率为 `(1-p)^N`。本例 p=10⁻⁵ 时理论值约 30%，1,000 次抽样观察到 32.6%。同一 BER 下，文件越大，至少一处出错的概率越高；不能把本表成功率直接用于其他文件长度。

## 2. 绕过外层校验：压缩数据能否继续解码

仅在独立试验程序内，向解析后的 z/y 压缩载荷注入错误。假定外层头部、帧边界、长度字段和元数据受保护，跳过外层文件及重建哈希判定；保留原生 rANS 长度、状态、逃逸符号和终止状态检查。y 内部的 12 字节熵流头仍属于随机载荷试验的错误范围。生产接收器没有改动。

每档 30 次，共 180 次：

| 设定 BER | 实际发生翻位的样本数 | 完整解码数 | 带错样本完整解码数 |
|---|---:|---:|---:|
| 0 | 0 | 30/30 | 0/0 |
| 1e-07 | 0 | 30/30 | 0/0 |
| 1e-06 | 5 | 25/30 | 0/5 |
| 1e-05 | 24 | 6/30 | 0/24 |
| 0.0001 | 30 | 0/30 | 0/30 |
| 0.001 | 30 | 0/30 | 0/30 |

表中 0/0 表示没有抽到带错样本，不能据此评价容错能力。所有完整解码样本都是零翻位样本；89 个实际发生翻位的随机载荷样本全部中断。

定点单比特及突发错误：

| 试验组 | 次数 | 完整解码数 | 中断前出现 RGB 改变的次数 |
|---|---:|---:|---:|
| single_f1_z | 8 | 0 | 0 |
| single_f1_y | 8 | 0 | 0 |
| single_f2_z | 8 | 0 | 0 |
| single_f2_y | 8 | 0 | 0 |
| single_f33_z | 8 | 0 | 1 |
| single_f33_y | 8 | 0 | 0 |
| burst_8_ | 8 | 0 | 0 |
| burst_32_ | 8 | 0 | 0 |
| burst_128_ | 8 | 0 | 0 |

`single_f33_z` 表示第 33 帧的 z 码本索引载荷翻一个 bit；`y` 单比特试验跳过内部 12 字节头，抽取第一个 rANS 分段的状态/编码字节。z 和 y 每种位置各 8 次，三帧共 48 次；这些都是抽样，不是遍历全部比特。三档突发错误每档 8 次，共 24 次。

合计 161 个带错载荷样本中，160 个在首个损坏帧中断，1 个在下一帧中断。不能把无法完整解码的样本赋为 PSNR=0 dB，也不能仅对幸存帧平均 PSNR 来表示整段成功。

## 3. 一个比特如何影响后续帧

`single_f33_z_1` 只翻转载荷的第 47,209 bit（从 0 计数，字节内从高位开始）。第 33 帧解出了图像，但参考状态改变；到第 34 帧，rANS 报 `status 6` 并中断。

第 33 帧相对**无误码 GLC 重建帧**的 PSNR 为 77.9415 dB、8 位像素 MAE 为 0.00104456，肉眼几乎看不出变化。这不是相对原始视频的压缩质量 PSNR，也不代表整段耐误码：当前帧视觉差异很小，后续解码仍会失败。预测参考状态和熵解码上下文需要编解码两端一致。

## 4. 能否在下一 I 帧恢复

额外进行了 6 次诊断：丢弃损坏的参考状态，显式定位到下一个干净 I 帧（第 65 帧），随后解码第 65、66 帧。6 次均与干净基线逐帧 RGB/参考状态哈希一致。

这说明在头部、帧位置和后续 I 帧受保护的前提下，可以设计分段恢复机制。**当前正式接收器并没有自动跳过坏帧恢复功能**；正常路径仍先拒收损坏文件。该诊断也没有恢复前面丢失的帧。reset_interval=32 只重置部分预测状态，不能视为独立 I 帧恢复点。

## 对文件传输和 Orin 部署的意义

GLC 压缩负责减少数据量，当前链路不具备纠错能力。对“传文件、希望总耗时较短”的目标，应同时测量压缩耗时、重传/冗余开销和最终完整解码成功率。更快的 GPU 不会纠正受损码流；更低的压缩码率也不等同于耐误码。

- 使用可靠传输，让解码器拿到校验通过的完整文件。TCP 用校验和、序列号和重传提供可靠有序字节流；链路错误通常表现为额外传输时间或连接失败，不能直接把物理 BER 当作解码器输入 BER。[RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)
- 如果使用不可靠链路，可评估按块校验、选择性重传，以及适合链路的前向纠错。SHA-256 校验只能检错，不负责修复；分块能避免一次局部损坏就必须重发整个大文件。
- 若希望部分数据丢失后仍能观看，需要额外设计独立 GOP/分段、受保护的索引与头部、错误隐藏及恢复策略。本次只验证了干净 I 帧重启的可能性，未实现这些功能。

未测试其他素材、码率、GOP、FP16/TF32 或 Orin；这些数字不可直接外推成某硬件/信道上的误码性能。也不能依据本实验断言 GLC 比 H.265 更耐错或更脆弱，需要相同信道、分包与保护条件下另做对照。

## 复现与校验

- `bench_glc_errors.snapshot.py`：实际运行的脚本快照；`manifest.json`：参数、源文件、版本及权重哈希。
- `strict_trials.jsonl`、`decoder_trials.jsonl`：每次翻位位置、帧号、失败原因；`payload_layout.json`：载荷与原文件字节映射。
- `baseline_validation.json`：66 帧干净解码与编码端 RGB/参考状态哈希、序列哈希全部匹配，接收端没有读取源视频。
- 未改变的前缀复用已验证的干净状态；发生错误后不再替换为干净参考。零翻位样本复用干净基线，未将它们当作新的 GPU 性能测试。
- `clean.glcv` 和 `single_bit_frame33.glcv` 均为 15,049 B，恰好差一个比特。后者保留原始外层校验值，正常接收器会拒收它；报告中的带错解码结果来自独立注入试验。
- `validation.json`、`summarize_ber.py`：不重新运行网络的结果交叉检查与报告生成程序；生产编解码文件哈希确认未变。
