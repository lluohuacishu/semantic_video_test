## 1. B 要回答什么

**用GLC恢复完整视频，在20／30／40 kbps的软件限速文件链路上完成真实收发，再验证语义信息能否改善鱼和潜水员的细节、轮廓及连续运动。**

工程目标是形成一个可重复执行的“编码→发送→接收→独立重建→观看与评价”闭环；研究目标是在计算全部发送字节后，验证按语义选择保护区域是否有收益。二者分别验收：传完文件不等于已经证明语义有效。

不再选择新的全画面压缩模型。首版不训练GLC或分割网络，不把JSCC、真实水声硬件、跨平台部署或新界面作为前置任务。实时性、最大文件大小和最大等待时间仍没有要求。

## 2. 首版方案

```text
源视频 ───────────────→ GLC全画面基础码流 ─────────────┐
   └→ 现有冻结语义模型 → 目标区域与时段 → 局部补充视频 ─┤
                                  位置/时间/版本/哈希 ─┤
                  完整通信包 → 20/30/40 kbps文件发送 → 接收
                    → 校验 → GLC解码 + 局部恢复与合成
                    → 接收端RGB帧、可播放视频和评估记录
```

第一版采用**GLC全画面基础层 + 由源帧编码的目标区域补充层**。局部补充层先复用已有FFmpeg/H.265编码和ROI时段/位置封装；它用于保护GLC可能改写的目标细节，不是重新选择主编码器。暂不实现新的学习残差模型，也不假装已有适配器支持GLC内部逐像素码率控制。

基础视频保留完整画面，避免漏检时目标只剩空白。首版区域布局复用已有分时段矩形与双区域逻辑，参数固定；暂不增加新跟踪模型。记录每个窗口的目标覆盖、跳变和边界，若实测发现问题，再只改动相关一项机制。

接收端需要预共享的GLC权重与匹配推理环境。旧H.265接收端“只需CPU／无需模型”的说明不适用于这条新路线。先沿用A已验证的同机FP32确定性环境；跨设备另行验证，不用一台机器上的两个进程冒充跨设备成功。

- 后续最多围绕明确失败点做少量配置修正，并说明原因；这不是重新打开A的路线选型。

语义模型及ROI配置已填写并完成严格加载、哈希核验；`null`仅保留在用户未设上限的文件大小与等待时间字段。每次运行保留输入配置快照，结果以该次`summary.json`为准，不能将运行前计数当作最新完成状态。

## 5. 试验材料与对照

先使用video91复现鱼纹问题；已有开发资料可调试，但不能作为新的独立留出结果。B3目标是至少三段来源可核查、彼此独立且未参与本轮调参的连续水下视频，每段尽量不少于10秒，合计覆盖鱼、潜水员、相机或目标运动。若素材不足，记录缺口；不将同一视频不同裁剪算作独立场景，也不把SUIM静态图串成视频。

在评价前固定帧范围、目标标签/核对项目和方案参数。GT只用于评价；人工／GT区域可作单独的诊断上界，必须与自动预测方案分开，不能冒充自动系统的结果。

| 对照 | 回答的问题 |
|---|---|
| GLC基础层 | 选定底座的原始失真是什么？ |
| GLC基础层 + 自动语义ROI补充 | 目标条纹、轮廓、动作有无改善，付出了多少字节与时间？ |
| 与增强方案总字节相近的全画面GLC | 收益是否仅来自增加文件大小？在合法q范围内做有界匹配，不能填充或截断码流 |
| 相同基础层、同样补充字节预算的固定几何区域 | 改善是否与语义选择有关？区域规则在看重建前固定，不按效果挑选 |
| H.265／AV1既有对照 | 继续作为工程参照；必要时补一个匹配点，不重跑大网格 |

完整文件预算匹配沿用±2%容差。GLC合法范围不能匹配时，记为“等预算不可达”并给实际差值；不同大小的结果只做质量—字节—等待时间比较，不能宣称等预算胜出。固定区域消融若预算无法匹配，也须显式标记。

## 6. 验收口径

### 工程闭环：必须满足

1. 20、30、40 kbps三档实际发送均有日志；文件、封装和发送方向应用层传输头计入统计。记录每次发送的累计字节与时间、理论最短发送时间、实测时间及平均速率。发送调度不得提前于累计字节对应的限速时刻；若有计时精度误差，单独给出，不用额外等待掩盖先突发发送。
2. 发送／接收文件SHA-256一致，接收端从实际收到的包独立解码；收到多少帧、尺寸、帧率和源帧序映射均正确，不丢帧、不偷偷缩短视频。B1首次目标为全部250帧通过。
3. 接收读取审计明确列出共享模型依赖，源媒体与发送端缓存读取为零；GPU／软件环境记录完整。代码级读取约束不能写成操作系统隔离。
4. 给出基础码流、局部补充流、区域坐标／时段、语义消息、容器和传输头分别的字节数。共享权重作为部署前置成本另列；若实验实际传权重，必须另计。
5. 输出接收端RGB和可播放视频。指标从接收RGB计算，观看副本的额外编码、正常速度／慢放分别标注。

以上是**软件应用层限速验收**。现有代码不统计TCP/IP、链路层或反向ACK字节，不是实际水声物理链路测试；报告必须保留该边界。当前传输模块有256 MiB实现上限，这不是用户的文件大小要求；小样本可先复用，若后续文件超过上限再做分块或配置化改造。

### 语义研究目标：必须拿出证据，不能预填成功

- 鱼／潜水员是否仍可见、数量和位置是否可信、轮廓与动作是否改变；条纹是本轮明确的问题样例。连通区域数不等于真实物体数，没有人工/GT时不填“真实计数准确率”。
- 目标区域PSNR／结构差异、固定分割器与GT的IoU作为辅助；同时给原图上的模型表现。分割IoU不降不能代替纹理保真。
- 正常速度与慢放核对目标忽隐忽现、条纹跳变、ROI边界闪烁及跨窗口突变；相邻误差变化只是诊断，不标为已验证的感知闪烁分数。
- 自动ROI覆盖和漏保护必须逐片报告，特别保留小目标和失败例；背景与上下文质量同时记录，不以牺牲它们制造局部平均提升。
- 只有在计算完整文件预算后，目标相关指标与真实观看核对共同支持改善，且没有新增严重目标或时序错误，才称为“语义保护有效”。没有真实观看答卷就写“待评”，不能生成用户评分。

完成工程链路但收益不成立时，分别写“工程通过、语义收益未证实”，保留负结果并定位瓶颈；这不自动推翻用户选定的GLC主方向，也不能写成B全部目标已达成。
